# 自适应计划 · 使用说明（阶段 3 按需加载）

> 配套 `SKILL.md`「自主决策层」。本文件回答两个问题：**复杂任务怎么拆**？**拆完在执行中怎么改**？
> 本文件属「方法定义」类文档，按阶段感知模型路由走 **mid** 档。

## 〇、与相邻文件的分工

| 文件 | 回答的问题 |
| --- | --- |
| 本文件 `adaptive-planning.md` | **怎么拆**（拆解规则）与**什么时候改**（重规划触发） |
| `assets/plan-template.yaml` | 拆完**写成什么格式**（字段与取值） |
| `capability-routing.md` | 每一步**要不要引入外部辅助** |

## 一、拆解四条规则

### 1. 右尺寸（right-sizing）：一步 = 一个最小可独立验证单元

判据三问，全过才是一个合格的步骤边界：

1. 它能**单独产出一个可判定的交付物**吗？
2. 若它需要返工，**会不会波及邻居**？（会 → 位置切错了，应合并或重切）
3. 它是不是**配套动作**？（配置、脚手架、文档、格式转换类动作**折进**它服务的那个步骤，不单独成步）

> 反例：把"建目录"、"写配置文件"、"更新文档"各自切成一步 —— 计划维护成本会超过执行成本。
> 正例：把"实现 A 并补齐 A 的配置与文档"合成一步，因为它们只能一起被验收或一起被退回。

### 2. 可验证前置：每步在**开工前**就要能说出"怎么算成了"

对应 `SKILL.md` 阶段 3 第 2 条。说不出可判定信号 → 先补一个最小验证物；补不了 → 显式登记**人审点**（不要假装有信号）。

| 反例（无信号） | 正例（有信号） |
| --- | --- |
| "实现 XX 功能" | "实现 XX 功能；信号：`pytest tests/test_<模块>.py` 退出码 0 且用例数 ≥ N" |
| "调研 XX 框架" | "调研 XX 框架；信号：≥2 个来源各带 URL + 关键链接探活 200 + star 数实测" |
| "优化性能" | "优化性能；信号：预热后多次取最小值，耗时下降**且**输出与旧版逐字节一致" |

### 3. 依赖显式化：拆完画一遍先后序

逐个问"谁必须先于谁"。**有依赖的严禁并行**（`orchestration.md` 并行规则第 2 条）。依赖关系要写进步骤的「输入」字段，让依赖**可被复核**而不是靠记忆。

### 4. 粒度可调：粗粒度给探索，细粒度给执行

| 任务性质 | 建议粒度 | 理由 |
| --- | --- | --- |
| **探索性**（路径未知、大概率会返工） | 粗（3–5 步） | 细拆会白拆，执行期必然大改 |
| **执行性**（路径清楚、按图施工） | 细（10+ 步） | 细拆能精确定位失败点 |

**不要在计划期假装知道执行期才知道的事** —— 探索任务被强行细拆，是重规划次数超标的头号原因。

## 二、动态调整（重规划）

### 2.1 触发条件（命中任一即**必须**重规划，不是"可以考虑"）

| 编号 | 触发条件 | 典型场景 |
| --- | --- | --- |
| **R1** | **新事实推翻原假设** | 实测发现目标库许可证不兼容；数据集字段与预期不符；star 数证明项目已停更 |
| **R2** | **验证信号不可达** | 原定判定方式跑不起来（依赖缺失／环境不支持）→ **换判定方式，而不是放弃判定** |
| **R3** | **中间产出暴露原计划未预见的依赖** | 出现新的前置步骤（"要先拿到凭据才能继续"） |
| **R4** | **成本超阈** | 某步开销远超预估（检索配额耗尽——即熔断 F5 的前置信号） |
| **R5** | **用户中途改需求** | 验收标准或交付物形态变化 |
| **R6** | **连续性断裂** | 会话中断／上下文丢失后重启，原计划与现实不再对应 |

### 2.2 **不**触发重规划（防过度重规划）

- 单次工具报错（未耗尽重试）
- 进度慢于预期但**路径正确**
- 发现了"更优雅的写法"但当前路径**仍可达验收标准**
- 用户的**澄清**而非**变更**（补问一句 ≠ 改需求）

> 判据一句话：**改的是"路径"，还是"目标/事实基础"？** 只改路径、且新路径不比旧路径更可靠时，不重规划。

### 2.3 重规划四步（次序固定）

```
① 停 —— 不在旧计划上继续叠加动作（否则产生"计划外的既成事实"）
② 记 —— 往 meta.计划修订 追加一条（见 2.4 格式），先留痕再改动
③ 改 —— 修订 steps：新增/删除/改序/改验证方式；**已完成步骤的原记录保留，不覆写**
④ 报 —— 一行告知："因 R<n> 调整计划：<变化>；已完成的 <k> 步不受影响"
```

### 2.4 修订留痕格式（追加，不覆盖）

```yaml
计划修订:
  - 版本: "v1 → v2"
    触发: "R1"
    时间: "2026-09-15 17:30"
    变化: "新增步骤 3b（先做许可证核查）；步骤 4 的验证方式由『人工核对』改为『checks.py plan 对账』"
    未变: "步骤 1-3 结论有效，步骤 5-6 顺序不变"
```

### 2.5 修订次数上限

同一任务重规划 **≤3 次**。超过 3 次说明**初始拆解方法本身有问题**，或该任务**不适合线性计划** → 停下来与用户对齐目标（这是**重新澄清**，不是熔断），不要继续在计划层打转。

## 三、状态可追踪（三层载体）

| 层次 | 载体 | 更新方式 | 记录内容 |
| --- | --- | --- | --- |
| **步骤状态** | `plan.yaml` → `steps[].状态` | `checks.py mark` | 待办／进行中／完成／受阻／熔断 |
| **能力决策** | `plan.yaml` → `meta.决策记录` | `checks.py decide` | 每次实际引入外部辅助：决策点／能力类／依据／选择 |
| **计划修订** | `plan.yaml` → `meta.计划修订` | `checks.py revise` 或手工追加 | 每次重规划：触发编号／变化／未变部分 |

三者合起来回答"**做了什么、为什么这么做、计划怎么变的**"。缺任何一层，事后都无法复算当时的判断。

> 说明：这三层是**留痕载体**，不是"每步都必须填满"的表单。`决策记录` 只在**实际引入能力**时追加（对应 `capability-routing.md` 第〇节定性）；一个纯本地读写的步骤不必产生决策记录。

## 四、执行期循环（每步固定六动作）

```
① 重述目标 + 判定标准               ← 防"做偏了才发现"
② 能力路由（capability-routing.md）  ← 需要则声明 + checks.py decide
③ 执行
④ 跑本步验证信号，出示**原始输出**    ← 不是"我认为没问题"
⑤ 更新状态（checks.py mark）
⑥ 判 R1–R6：命中 → 走 2.3 四步；未命中 → 下一步
```

## 五、反模式清单

| 反模式 | 症状 | 后果 |
| --- | --- | --- |
| 过细拆解 | "打开文件"也算一步 | 维护计划的成本超过执行成本 |
| 过粗拆解 | "完成整个后端" | 失败后无法定位到具体步 |
| 无信号步骤 | 完成后无法判定"成了" | 交付时必然扯皮，只能靠嘴说 |
| 静默改计划 | 改了 steps 不记修订 | 事后无法解释"为什么少做了一步" |
| 依赖倒置 | 把需要 A 产出的 B 并行派出 | 结果错乱且难以归因 |
| 重规划成瘾 | 一遇小阻就重排 | 永远停在计划期，交付遥遥无期 |
| 假确定性 | 把语义判断写成脚本 | 脚本跑绿了但结论是错的 |
