# 方法选用 · 快判（method-judge，v4.4.0 新增）

> **定位**：ai-workflow 在**每一个需要选工具/方法的步骤之前**必跑的一个 **System 1 结构化判别**模块——动手之前先判一次「这一步缺哪类能力、该用哪个具体工具、置信多少」，据此规范后续「选什么手段」。它是 `self-judge`（入口级：判"这是什么任务"）的**步骤级孪生**：self-judge 决定走哪条路，本模块决定每一步踩哪块砖。
> **它是红绿灯，不是车**：只输出「该用什么工具/方法」，不产出具、不授权、不越界、不替代安全关键门禁。
> **配套（机器侧随 v4.4.0 一同新增，v4.4.0 修订为列表）**：判定结果**逐条追加**到 `assets/plan-template.yaml` 的 `meta.方法选用` 列表（每步一条，与 `meta.决策记录` 同构）；机器校验见 `scripts/checks.py plan` 检查项 14。
>
> ⚠️ **哲学来源**：Jev（TypeSafe AI 的 System One 模型）三原语 Choice / Score / Noul + 校准概率 + fail-closed + 判定即结构。设计依据为工作区**三份** JEV 设计文档（理念层 / 集成方案 / 借鉴清单），以及 `capability-routing.md`（本模块的能力类词汇源）。
> ⚠️ **不做落地层（明确约束）**：与 self-judge 同，**默认 Realization A（脑内协议）**——由主代理 LLM 自我约束产出结构化判定，**不训独立决策模型**（不建 OpenJev / Qwen 复现、不做 speculative fan-out 并行门禁）。借鉴清单 §2 的「本地 DecisionNode 复现」路线**本版不启用**。

## 1. 定位与形态

| 项 | 值 |
| --- | --- |
| **模块名** | `method-judge`（中文：**方法选用 · 快判**） |
| **形态** | ai-workflow 的**内部子模块**（非独立顶层 skill）；本文件即其完整契约，由阶段 3 执行期六动作第②步（能力路由）加载 |
| **本质** | 纯判别（System 1）：**单次前向、无 chain-of-thought、无自回归展开** |
| **主语** | "模型给这一步选手段做判断"——判的是「**这一步该用什么工具/方法**」，不是"我能不能做" |

**能力类（Choice，四类，源自 `capability-routing.md` §一）**：

| 类 | 含义 | 典型手段 |
| --- | --- | --- |
| **知识** | 需要专门方法论/领域流程 | 加载其它 skill |
| **算力（隔离）** | 子任务独立、可并行、需独立视角 | 派子代理 |
| **事实（外部）** | 需要本机推不出的当世事实 | 联网检索 / `http_fetch` / `gh api` / `data_query` |
| **手脚（执行）** | 需要确定性计算/结构解析/批量产出 | `scripts/` / 本地工具 / MCP 连接器 |

> 本模块的 **`gap_class` 取值域就是上表四类**（可组合，如 `事实+手脚`）；**不另造一套**。上表的判据（该用/不该用）由 `capability-routing.md` 独家持有，本模块只做"按该判据出结构化判定"，二者**判据同源、职责正交**（沿用「技能库卫生」第 4 条）。

### 1.1 与「能力路由」的关系（**两层正交，不是替换**）

⚠️ **这是一处对设计文档的收敛，理由写在下面，请勿当成笔误。**

设计文档曾建议把"能力路由"直接改为 Jev 式快判。本契约落地为**两层并存**，因为二者是**正交的两根轴**：

| 轴 | 问题 | 落盘位置 | 决定的后果 |
| --- | --- | --- | --- |
| **能力路由（判据手册）** | 缺哪类能力、该类**该用/不该用**的判据是什么？ | 不落盘（纯手册，模型按标准想） | 提供**词汇与判据知识** |
| **method-judge（判定契约）** | 这一步**实际选了哪个工具**、置信多少？ | `plan.yaml` 的 `meta.方法选用` | 提供**结构化、可回溯、可加判据的判定产出** |

> 即：`capability-routing.md` 告诉你"知识类该用 skill、事实类该联网"；`method-judge` 在每一步把"我这一步判为事实类、候选 `gh api` fit=0.9 / `web_search` fit=0.6、needs_tool=true、confidence=0.96"落成结构。**判据在手册，判定在契约**——这正是 self-judge 与入口分型「两层正交」的同构处理。

## 2. 触发条件

| 场景 | 是否触发 | 说明 |
| --- | --- | --- |
| 阶段 3 任一步骤涉及**选择工具/方法/能力**（绝大多数步骤） | **必触发** | 取代"凭习惯随手选工具" |
| 纯内联推理、明确不需要任何外部工具/脚本 | **不触发** | `needs_tool=false` 即结论，不写决策记录（同能力路由硬规则4） |
| 已在子代理内部 | **不触发** | method-judge 作用于主代理的步骤级选工具，不混入子代理内部 |
| 用户明示「直接做 / 别走流程」 | **触发后遵从授权** | 判定留痕供回溯，不改变用户授权语义 |

**主动克制（判定阶段禁止做的事）**：不触发重检索、不读全库、不派子代理、不展开思维链——否则退化成 System 2，失去"快"的意义。输入只需本步的「做什么 / 输入 / 预期产出」三字段。

## 3. 执行步骤（单次前向、四步、无自回归）

```
① 解析 ：本步「做什么 / 输入 / 预期产出」→ 结构化需求态  —— 不触发重检索
② 评估 ：并行打分 5 个正交维度 M1–M5 → 各维 Score(0–1) 或 Noul(P(true))
③ 选择 ：Choice 能力类（知识/算力/事实/手脚，可组合）+ 该类下候选工具及 fit_score
④ 二值 ：Noul 判定「needs_tool」→ 输出结构化判定
```

四步**全为单次前向**。第③④步共用同一次判别，不得为"提高准确率"而多次采样（Realization A 下多次采样即多付一次前向；Realization B 才允许并行 fan-out，见 §7）。

### 3.1 判定维度 Schema（Schema-First：先定义维度，再判定，固定不临时发挥）

| 维度 | 含义 | 原语 | 高分指向 |
| --- | --- | --- | --- |
| **M1 确定性需求** | 本步判断能否由脚本/工具**确定性**完成（计算/解析/批量） | Score | 手脚 / 事实 |
| **M2 语义需求** | 是否需要**语义理解/领域判断**（非确定性的"想清楚"） | Score | 知识 / 算力 / 人工 |
| **M3 时效/外部性** | 是否需要**当世事实/外部数据**（本机推不出） | Score | 事实 |
| **M4 独立性/并行性** | 子任务是否**独立、可并行**、需独立视角 | Score | 算力 |
| **M5 本机可得性** | 所需事实/工具**工作区内是否已有**（Grep/Read 够不够） | Score | **高分=不联网**（反向指针） |

> M1–M4 是**语义维度**，决定能力类；M5 是**效率指针**，只作校正（本机已有就不联网，呼应能力路由"只读先于写入、本地先于联网"）。

### 3.2 三原语在方法选用中的对应

| Jev 原语 | 语义 | 本模块中的角色 |
| --- | --- | --- |
| **Choice** | 从 N 个里选 | ① 能力类 `gap_class`（知识/算力/事实/手脚，可组合）② 该类下的候选工具 `candidates[].tool` |
| **Score** | 连续位置 + 置信 | `candidates[].fit_score`（每个候选对本步需求的契合分 0–1）；M1–M5 维度分 |
| **Noul** | P(true) 是非判断 | `needs_tool`（这步到底需不需要外部工具）；M5 的本机可得性 |

> ⚠️ **Noul 语义陷阱**：`P(true)` 本身就是信念强度，**不要把它当"置信度字段"再套一层阈值**；Score 的等级顺序写反是另一处高频坑。

## 4. 输入输出契约（Contract）

**输入（最小化；判定阶段不取额外上下文）**：

```yaml
step_what:   str          # 本步「做什么」
step_input:  str          # 输入来源
step_expect: str          # 预期产出
```

**输出（机器可读，逐条追加到 `plan.yaml` 的 `meta.方法选用` 列表，与 `meta.决策记录` 同构——每步一条判定）**：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `gap_class` | `知识`\|`算力`\|`事实`\|`手脚`（可 `+` 组合） | ✔ | Choice 能力类。**词汇唯一取值源见 `capability-routing.md` §一** |
| `candidates` | `[{tool, fit_score}]` | ✔ | Choice(2..k) + Score：每个候选工具及其契合分（0–1） |
| `needs_tool` | bool | ✔ | Noul：这步到底需不需要外部工具（false → inline 做，不写决策记录） |
| `confidence` | float 0–1 | ✔ | = max(fit_score) 或主类置信 |
| `route_hint` | str | ✔ | 处理指引（见 §5），非空 |

**字段化而非散文**，是为了对齐 ai-workflow 既有的"机器可校验"风格（`入口判定`/`模型档位`/`自研工具` 等同构）：判定结果可进账本、可回溯、可未来加判据。

## 5. 阈值路由（Threshold Routing）

| 区间 | 行为 |
| --- | --- |
| `needs_tool=false` | **不引入、inline 做**；**不写决策记录**（沿用能力路由硬规则4：不引入是合法且常见结论） |
| `needs_tool=true` 且 `confidence ≥ 0.95` | **自动选用** top candidate（fit_score 最高者） |
| `0.70 ≤ confidence < 0.95` | **中置信**：选 top 但**标记待复核**，或单句确认与次选差异 |
| `confidence < 0.70` **或** 候选间 fit_score 差距极小（歧义） | **fail-closed**：问一句"你倾向 X 还是 Y"，或选**最安全默认**并标记 |

**`route_hint` 按结论给出处理指引（规范后续选手段的核心产出）**：

| 结论 | route_hint | 动作 |
| --- | --- | --- |
| 不引入 | inline 执行 | 直接做，不派能力 |
| 自动选用 | 选用 `<tool>` | 用 top candidate；写一行声明 + 一条决策记录 |
| 中置信 | 选用 `<tool>`（待复核） | 用 top 但标记，或确认备选 |
| 模糊/歧义 | 澄清 | fail-closed：问一句，不猜 |

> ⚠️ **校准优先于准确率**：一个 67% 准确率但**完美校准**的判定器，比 90% 准确率却**错标**的更有路由价值——路由靠"概率可信"。这正是阈值取保守值（自动采信 0.95）的**理由**。
> ⚠️ **校准未经独立证实前，阈值取保守值**（自动采信 0.95、中置信一律走复核/澄清）——"自信地选错工具"比"不判"更危险（错用脚本会造假确定性）。
> ⚠ **低置信档取「澄清 / 选最安全默认」**：借鉴清单 §2.3 的通用表写"转人工/升前沿 LLM"；但本模块低置信只意味"没想清这步该用什么手段"，澄清一句或退回最保守手段（如用确定性脚本而非语义判断）更轻更对症。

## 6. 集成位置与机制

method-judge 嵌入阶段 3 执行期六动作，**落点 = 第②步（能力路由）之前**：

```
阶段 3 每步：
  ① 重述目标与判定标准
  └─► [method-judge 触发] → {gap_class, candidates, needs_tool, confidence, route_hint}
        └─► 写入 plan.yaml 的 meta.方法选用（与 meta.决策记录 同构；needs_tool=true 时才追加决策记录）
              └─► 驱动：
                    (a) 能力类选择（知识/算力/事实/手脚，映射自 capability-routing.md）
                    (b) 具体工具选择（candidates 里 fit_score 最高者）
                    (c) 是否引入外部辅助 / 是否需澄清
```

### 6.1 与各组件的协作方式

| 协作对象 | 关系 | 协作方式 |
| --- | --- | --- |
| **能力路由（`capability-routing.md`）** | **判据源 + 正交并存** | 它给"该类该用/不该用"的判据；本模块给"这步实际选了什么"的判定（见 §1.1） |
| **`plan.yaml` / `checks.py plan`** | 留痕载体 | 判定落 `meta.方法选用`；检查项 14 校验（缺失 → WARN，见 §10） |
| **`meta.决策记录`** | 决策留痕 | `needs_tool=true` 时追加一条 `{决策点, 能力类, 依据, 选择, 时间}`（用 `checks.py decide`），与能力路由声明制同源 |
| **阶段感知模型路由** | 下游 | 选定能力后，才定用哪一档模型（strong/mid/cheap），二者按序 |
| **子代理编排（`orchestration.md`）** | 下游 | 能力类=算力 → 才进 Handoff 派发细节 |
| **红线③ / 出站扫描 / 口径守卫** | **不替代** | 安全关键门禁仍由确定性 AST/代码兜底，见 §8 |
| **self-judge** | 上下级 | self-judge 判"任务是什么"（入口级）；本模块判"每步用什么工具"（步骤级）；二者同构、不互相覆盖 |

### 6.2 接进 `checks.py decide` 的决策留痕流程（v4.4.0 修订）

`meta.方法选用` 与 `meta.决策记录` **都是列表、同构**（每步一条）。`needs_tool=true` 的判定应落为一条决策记录——不必手填四项，`decide` 直接从 `meta.方法选用` 推导：

```bash
# 手动四参数（旧写法仍可用）
python checks.py decide plan.yaml --point "步骤3缺什么" --basis "一句话判据" --capability 事实 --choice "gh api …"
# 从方法选用推导（推荐）：读 meta.方法选用 列表最新一条，自动取 能力类←gap_class / 选择←fit_score 最高的 candidate / 依据←route_hint(+confidence)
python checks.py decide plan.yaml --point "步骤3" --from-method-select
python checks.py decide plan.yaml --point "步骤3" --from-method-select 2   # 指定第 2 条（1-based）
```

- 推导项可被同名参数覆盖（`--capability` / `--choice` / `--basis` 显式给出则优先）。
- `--point`（决策点/步骤名）**必须手填**：`meta.方法选用` 只存方法选用判定，不记录步骤名。
- `needs_tool=false` 的判定**不要**走 decide（"不引入"是合法结论，见 §2、硬规则4）；`checks.py plan` 的一致性 WARN 会提示「needs_tool=true 却无对应决策记录」的漏记。
- 能力类校验放宽接受「+」组合（如 `事实+手脚`），与 `gap_class` 同词汇。

## 7. 判定模型：双 Realization（由谁/什么执行判断）

### 7.1 结论：基础设计**不需要**独立训练的神经网络

method-judge 的目的是"规范模型每步选手段的思考顺序"，由**主代理 LLM 自身**在动手前强制执行一次结构化快判即可达成——直接长在"大脑"里，**无需额外权重**。这是默认 realization。

但**必须显式定义"判定模型"**，否则"单次前向、无思维链"只是口号、落不到执行主体。故采用**双 realization**（与 self-judge §7 同构）：

| 维度 | **A 脑内协议**（默认，**本版启用**） | **B 独立 System 1 模型**（升级，**本版不启用**） |
| --- | --- | --- |
| 是否新增权重 | 否 | 是 |
| 与"大脑"耦合 | 同源，最贴"集成到大脑" | 解耦，作为外部快判节点 |
| 校准概率 | 间接（纪律 + few-shot 诱导） | 直接（RLCD 式校准目标） |
| 并行 fan-out | 不支持 | 支持（一次前向打包多个门禁） |
| 适用规模 | 单步、低频 | 高频、批量、需解耦 |

### 7.2 Realization A —— 脑内协议（默认，零新增依赖）

- **不是新模型**，而是主代理 LLM 的**自我约束协议**：把 §3 的四步判据写进阶段 3 第②步，强制其产出 §4 的结构化判定。
- **"模型"即推理纪律**：判定能力来自 LLM 既有的意图理解，由 schema + §9 判例锚 + fail-closed 兜底诱导出稳定输出；**无单独训练、无单独权重**。
- **诱导目标**：让判定分布尽量"校准"——手段 ① 固定 5 维 schema（防临场发挥）② §9 判例锚定边界 ③ 低置信强制澄清。
- **代价（诚实登记）**：未与执行解耦 → 判定不独立校准、不可并行多问、占用主模型一次前向。

### 7.3 Realization B —— 独立 System 1 决策模型（升级路径，**本版不启用**）

- **何时启用**：① 高频批量选工具 ② 判定与主模型解耦以降成本 ③ 真正并行的 speculative fan-out（一次前向打包"越界?+口径?+方法?"多个门禁）④ 独立校准概率驱动阈值路由——此时 A 的前向成本与不可并行成为瓶颈。
- **本地落地**：官方 Jev API **未向中国大陆开放**，不直连；若启用 B 走社区复现（OpenJev 冻结 Qwen3.5-4B + 受限 softmax；APUS `fast-browser-use`，MIT）。
- **接口**：与 §4 **完全一致**，故 A ↔ B 切换对下游透明。

> **落地顺序（用户明确约束）**：**只上 A**，不启用 B。借鉴清单 §2 的「本地 DecisionNode 复现」「fan-out 并行门禁」「把 P0 三项硬门禁替换为决策模型」**本版不做**，仍是设计稿。契约不变，未来启用 B 不改下游。

## 8. 不可委派与护栏

- **不授权写操作**：只输出"该用什么工具"，**不输出"我可以做"**。工作区边界红线、写操作确认仍归确定性规则与人工。
- **不替代安全关键门禁**：红线③越界判定（`_check_scope`）、出站扫描（`scripts/outbound_scan.py`）、口径守卫（`_check_parity`）、自研工具漏登记检测，保留 AST/代码实现，method-judge 仅作辅助信号。
- **语义判断不外包给脚本**：若 `gap_class=知识` 且需要语义判断，仍由模型做，不塞进脚本（呼应能力路由硬规则2：语义判断塞进脚本=假确定性）。
- **不越界**：判定只读本步的「做什么/输入/预期产出」，不读全库、不触发重检索。
- **理由**：概率校准尚未独立证实、且**可在 schema 内高置信选错**；安全/不可逆动作不能押在 unverified 模型上。

## 9. 判定样例锚（边界判例，供 Realization A 的 few-shot 锚定）

> 作用：把"该选什么工具"的边界锚成**可复用判例**，而不是每次临场发挥。列 5 条种子判例，首次使用后可继续追加。

| # | 本步「做什么」 | gap_class | candidates（fit_score） | needs_tool | 备注 |
| --- | --- | --- | --- | --- | --- |
| 1 | "合并三份 CSV 成一份" | 手脚 | `scripts/data_query.py`(0.95) / `pandas`(0.7) | true | 高置信→自动用 data_query |
| 2 | "查一下这个库现在的 star 数" | 事实 | `gh api`(0.9) / `web_search`(0.6) | true | 中置信可复核；本机推不出→必联网 |
| 3 | "想想这个数据有什么问题" | 知识 | 人工语义判断(0.8) | false | **needs_tool=false**：纯推理，inline 做，不写记录 |
| 4 | "三个方向并行调研竞品" | 算力 | 子代理(只读)(0.95) | true | 独立可并行→派子代理 |
| 5 | "既查事实又解析结构" | 事实+手脚 | `gh api`(0.9)+`scripts/data_query.py`(0.9) | true | **组合类**：主类承载、次类作子阶段 |

**判例 3 是重点**：`needs_tool=false` 不是"判不出来"，而是"这步本就不需要外部工具"——合法且常见的结论，不写决策记录。

## 10. 诚实边界与验收

沿用本技能一贯的"诚实边界"风格：**写在提示里的门禁不是门禁**。

1. ⚠️ **校准不可机器强制** —— `confidence` 由模型自填，**无法被工具证明"真的校准"**。它是**纪律 + 留痕项，不是门禁**。任何"已由工具保证校准"的说法都不成立。
2. ⚠️ **缺失 `meta.方法选用` 不是 FAIL，是 WARN** —— `checks.py plan` 检查项 14 的口径：整段缺省 → **WARN**（向后兼容旧 plan，**不追认历史计划**）；一旦填写，结构非法 → **FAIL**（沿用"可选字段、填了就不能糊弄"）。**不得宣称该字段是强制门禁。**
3. ⚠️ **判定也会判错** —— 下游必须可观测、可复核；判定结果随步骤留痕（`meta.方法选用`），便于回检"当时为什么选这个工具"。
4. ⚠️ **类型合法 ≠ 判断正确** —— 本模块保证输出**落在 gap_class 四类之内**（零类型错误），**不保证工具选对**。"选了工具"≠"工具对"——把"格式合规"误读成"结论可信"正是 `checks.py plan` 第 11 项曾三次被误读成绿的同一种根因。
5. ⚠️ **判错比不判更危险** —— 故低置信一律降级到"澄清/选最安全默认"（fail-closed），自动采信阈值取保守值 0.95。

**验收信号（可判定）**：

| 信号 | 判定方式 |
| --- | --- |
| 含工具选用的步骤，其 `plan.yaml` 含 `meta.方法选用` 且 `gap_class` ∈ {知识,算力,事实,手脚}（+组合） | 机器（`checks.py plan` 检查项 14） |
| `needs_tool=false` 的步骤确实没写决策记录 | 人审（查 `meta.决策记录` 是否多余） |
| 抽样历史步骤，工具选用与人工复核一致率 | **人审** —— `checks.py plan` **检查项 15**（`_check_method_select_sample`）只做**机器指路**：把**抽样池**（`needs_tool=true` 或 `confidence < 0.95` 的条目）列出来出 WARN，**判定仍靠人**。未证实前只报"**一致率**"，**不声称"准确率"** |

> ⚠️ **检查项 15 是"指路"不是"门禁"**：它把"该抽样看哪里"标出来，**不判定"选得对不对"**（机器做不到），故**永不计入 FAIL、不改退出码**。它把 §10 第 4/5 条（类型合法 ≠ 判断正确、判错比不判更危险）从"提醒"变成"每次 plan 检查都出现的一次指路"，但**不改变"正确性只能靠人复核"这一事实**。
