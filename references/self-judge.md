# 自我判断 · 意图快判（self-judge，v4.2.0 新增）

> **定位**：ai-workflow 在**每一次任务最前端**必跑的一个 **System 1 结构化判别**模块——动手之前先判一次「这是 chat / code / content」，据此规范后续思考顺序（先判类 → 再选层 → 再定档 → 再执行）。
> **它是红绿灯，不是车**：只输出「这是什么」，**不产出具、不授权、不越界**。
> **配套（机器侧随 v4.2.0 一同新增）**：判定结果落 `assets/plan-template.yaml` 的 `meta.入口判定`；机器校验见 `scripts/checks.py plan` 检查项 13；主类枚举的口径守卫见 `checks.py skill`（手册 ↔ 代码同源）。
>
> ⚠️ **版本自证（读到不一致时以本段为准）**：本文件所称的机器侧配套——`checks.py plan` **检查项 13** / **`VALID_CATEGORY`** 常量 / 口径守卫的「**入口判定主类**」项——**随 v4.2.0 一并新增**。若你读到此处却发现 `checks.py` 的 plan 子命令**仍只有 12 项**，说明本版处于**半落地**状态，须先补齐机器侧再引用本文件；**不要**据此认为本文件写错了。
> **哲学来源**：Jev（TypeSafe AI 的 System One 模型）三原语 Choice / Score / Noul + 校准概率 + fail-closed。设计依据为工作区**三份**设计文档（理念层 / 集成方案 / 借鉴清单，见附录 A）。

## 1. 定位与形态

| 项 | 值 |
| --- | --- |
| **模块名** | `self-judge`（中文：**自我判断 · 意图快判**） |
| **形态** | ai-workflow 的**内部子模块**（非独立顶层 skill）；本文件即其完整契约，由阶段 0 第 1 步加载 |
| **本质** | 纯判别（System 1）：**单次前向、无 chain-of-thought、无自回归展开** |
| **主语** | "模型给自己的请求做判断"——判的是**用户这次要我产出什么**，不是"我能不能做" |

**主类别（Choice，三选一）** —— 本表即**机器可读声明块**（下方一对 ASCII 标记圈定，须在**源规格面内恰一处**：源规格＝`SKILL.md`＋`references/*.md`＋`assets/*.md`＋`assets/*.yaml`，**不递归**），与 `scripts/checks.py` 的 `VALID_CATEGORY` 经口径守卫（`checks.py skill` 的「入口判定主类」项）同源，**读不到块即 FAIL**。
>
> ⚠️ **其他文档（含 `SKILL.md` 阶段 0）可以引用主类名，但不得引入本表之外的类别**。判据分两半，**各自只声明自己扛得住的那部分**：**① 确定性（FAIL）＝ 紧贴下表的一对 ASCII 标记圈出的「机器可读声明块」**（`<!-- ai-workflow:category-decl:begin -->` / `…:end -->`，须**整行**出现）—— 块须在**源规格面内恰一处**（即与 `SKILL.md`、`references/*.md`、`assets/*.md`、`assets/*.yaml` 一起数；技能根目录、`scripts/`、`references/` 子目录、`assets/*.txt`／`assets/templates/` **不在扫描面内**），块内取值集合必须**恰好等于** `VALID_CATEGORY`；块读不到、块形不合法、取值不符 → 一律 FAIL。**块形契约**：表头 + 分隔 + ≥1 数据行，且**每个数据行首格须整格一个裸词**（**空首格亦不合法**；写 `**chat** / **image**` 这类**连写／多值／带后缀**会被判「块形不合法」→ FAIL）。**故在「首格是裸词」这一前提下，块内新增第四类、改错大小写、删一行、把取值写成连写，都会被机器抓到。** ⚠️ 上面这条一致性断言是**同源断言，不是策略断言** —— 它只防「改一处忘一处」；若把 `VALID_CATEGORY` 与块内取值**同时**改成含第四类，两处一致即通过（**设计内行为**：本模块不预设「主类必须恰好三个」）。 **② 启发式（WARN，不作门禁）＝ 源规格面内「主类疑似列」扫描** —— 连续表格行视为一张表，某列裸词里属于本枚举者过半即认该列为疑似列，其可疑取值（枚举外）报 **WARN** 并附文件名与行号。**刻意只报 WARN**：启发式会漏会误，拿来当门禁就会变成假绿源或随机 FAIL 源。（它还只对**行列整齐**的表生效：列数不一致的表整表跳过 —— **宁漏不误**。）
> **仅提及主类名以指路是允许的**（如 `description` 的触发锚、索引表的"主类枚举见本文件"），否则 `description` 会失去可匹配性（见「技能库卫生」第 2 条：description 是唯一被自动匹配的字段）。
> ⚠️ **确定性那一半只覆盖声明块内** —— 块外任何位置新写一张「主类表」都**不会 FAIL**；**仅部分写法**会在启发式 WARN 露面 —— 实测**同一批块外夹具里只有约 1/4–1/3** 会露面（两轮独立测量：3/14 与 5/18，**夹具集不同、不合并**），其余两半全绿，故**大体靠人审**。**历史必读（别改回去）**：v4.2.0 前四轮曾用「全手册找表头 `| 主类 |`」的解析来做 FAIL，被独立复核（**未参与实现者**）实测出 **14 种假绿 + 2 种误报**（表头 `**主类**（认知轴）` 组合写法、取值大写／带连字符／全角／零宽字符、引用块 `>`、缺首尾竖线……），且 §10 描述守卫射程的那一行因格内引用了 `| 主类 |`，按竖线切分后产生恰为 `主类` 的碎片格而被**误判成表头**（哑雷）。**结论：「从任意 markdown 表格里稳定提取枚举」这个前提不成立 → 改口径，不再加固正则。**　**又一条已声明的漏**：启发式只认「**整格恰好是一个裸词**」的表格 —— **斜杠连写式重述**（`chat / code / content`，而 `assets/` 里正是这么写的）**在块外不判**（块内已由上面的块形契约判 FAIL）：实测把格子按 token 拆开扫，真文档上会**成片误报**（`Bug`／`secondary`／`ambiguity`／`true`／`LLM`／`fail-closed`／日期串……，且**处数随扫描面变动、不可复现为定值**），故按**宁漏不误**放弃该写法，这类重述靠人审。**已声明的盲区共三条**：① 斜杠连写不判（本段）；② **列数不齐的表整表跳过**；③ ⚠️ **块外主类表紧跟另一张表（中间不留空行）时会被并成一张表** —— 此时能否被扫到**取决于合并后该列的裸词占比**：当前表贡献的枚举外裸词够多时会被并掉而**静默**，不够多时反而**会出 WARN**（并可能捎带报出前一张表里的裸词）（两向均由第三轮独立复核实测；机制见 `checks.py` 的 `_scan_one_table`）。**故块外新写主类表请与前一张表空一行，并且不要据 WARN 有无来判断「有没有漂移」。**
> ⚠️ **配套约束**：标记必须**整行**出现。故在别处讨论本机制时请用反引号包裹（如 `` `<!-- … -->` ``），**不要让标记单独成行** —— 那会被计成「第二处声明」而 FAIL。

> D1–D4 是**语义维度**，决定类别；D5 是**句法线索**，只作校正、不单独定类——防止被"帮我写个……"这类措辞误导。

### 1.1 与「入口分型」的关系（**两层正交，不是替换**）

⚠️ **这是一处对设计文档的收敛，理由写在下面，请勿当成笔误。**

设计文档 §11 曾建议把阶段 0 的「消息 / 正式需求 / Bug」三态**改为** chat/code/content。本契约落地为**两层并存**，因为二者是**正交的两根轴**：

| 轴 | 问题 | 取值 | 落盘位置 | 决定的后果 |
| --- | --- | --- | --- | --- |
| **self-judge（认知轴）** | 这次要我**产出什么**？ | chat / code / content | `plan.yaml` 的 `meta.入口判定` | 任务分层 L0/L1/L2、模型初始档位、是否落 plan |
| **入口分型（来源轴）** | 请求**怎么来的**、带不带现有产物？ | 消息 / 正式需求 / **Bug** | **无落盘字段**（v4.2.0 之前该信息写在 `Ledger.md` 的「入口类型」列；v4.2.0 起该列**改由 `meta.入口判定.category` 提供**，故来源轴不再有落盘点） | 选择**侧重**（下表三条），其中 Bug 附带强制闭环 |

来源轴的三条侧重 —— **均无法由 `category` 推出**，这正是"两层正交"的理由：

| 入口 | 侧重 |
| --- | --- |
| **消息类** | 侧重阶段 1 **补上下文**（追问补齐来源/目标），允许先出草案再迭代 |
| **正式需求** | 走完整六阶段；**阶段 2 方案评审必做** |
| **Bug/缺陷** | 强制「复现 → 根因定位 → 修复 → 回归验证」闭环；**禁止未复现就改** |

**若把 Bug 三态合并进 chat/code/content，Bug 的强制闭环会被吞掉** —— 一份 Bug 报告在主类上通常仍判 `code`、照常进 L2，但 L2 的**通用流程不含**"必须先复现、未复现不得改"这条专项纪律；该纪律挂在"请求来源 = 缺陷报告且带现有产物"上，**合并即触发点消失**。

故：**self-judge 前置，入口分型保留，两层不得互相覆盖**。二者**落盘口径不同**：self-judge 落 `meta.入口判定`；**入口分型本版不为它新增任何字段**（plan 层与台账层都不新增）——它的作用在**选择侧重**与**触发 Bug 闭环**，**不改动 `meta` 结构、也不占用 `Ledger.md` 的列**（该列已改由 `category` 提供，见 §6.1）。

> **命名规则（v4.2.0 起，防同名不同义）**：「**入口类型**」此后**专指认知轴**的 `category`；**来源轴**（消息 / 正式需求 / Bug）称「**来源分型**」——`assets/ledger-template.md` 的命名规则表是唯一口径源，`assets/熔断报告模板.md` 的对应字段已随之改名。**同一个词不得同时指两件事**（呼应「技能库卫生」第 4 条：同一物理量的判据跨模块必须同源）。

## 2. 触发条件

| 场景 | 是否触发 | 说明 |
| --- | --- | --- |
| 用户请求进入 ai-workflow 处理（阶段 0 第 1 步） | **必触发** | 取代"凭措辞经验随手判 L0/L1/L2" |
| 请求明显属 L0（「翻译这句」「读一下某文件」） | **触发但可秒达** | 判 `chat` 高置信 → 直接答；**为留痕仍跑一次**，但不必落 plan |
| 用户明示「直接做 / 别走流程」 | **触发后遵从授权** | 判定结果留痕供回溯，**不改变**用户的授权语义 |
| 已在某工作流中途的子步骤 | **不触发** | self-judge 只作用于**任务入口**，不作用于执行期子步（不混入阶段 3 闭环） |

> **与红线的接缝**：触发 self-judge **不改变**三条红线——不改变「用户确认前不执行」（红线①）、不改变「计划先行」（红线②）、不改变「工作区边界」（红线③）。它只决定"走哪条路"，**不决定"能不能越界"**。

**主动克制（判定阶段禁止做的事）**：**不触发重检索、不读全库、不派子代理、不展开思维链** —— 否则就退化成 System 2，失去"快"的意义。输入只需用户原始请求文本 + 极少量上下文。

## 3. 执行步骤（单次前向、四步、无自回归）

```
① 解析 ：用户原始请求 → 结构化意图态（动作 / 对象 / 约束）  —— 不触发重检索
② 评估 ：并行打分 5 个正交维度 D1–D5 → 各维 Score(0–1) 或 Noul(P(true))
③ 选择 ：Choice 主类 + 校准分布 {chat, code, content}（三者之和 = 1）
④ 二值 ：Noul 判定「是否模糊 / 混合请求」→ 输出结构化判定
```

四步**全为单次前向**。第③④步共用同一次判别，不得为"提高准确率"而多次采样（Realization A 下多次采样即多付一次前向；Realization B 下才允许并行 fan-out，见 §7）。
>
> ⚠️ **此处相对集成方案 §2.5.2 有一处刻意收敛**：该节把「**自我一致性**（self-consistency，多次判定取一致分布）」列为 Realization A 的诱导手段；本契约**不采用** —— 它与集成方案 §2「纯判别、**单次前向**、无自回归」**不可同时成立**（同一份设计文档在此处自相矛盾）。A 的诱导手段收敛为本文件 §7.2 所列**三项**；"并行多问"只属 Realization B 的 fan-out。

### 3.1 判定维度 Schema（Schema-First：**先定义维度，再判定**，固定不临时发挥）

| 维度 | 含义 | 原语 | 高分指向 |
| --- | --- | --- | --- |
| **D1 交付物明确性** | 请求是否指向一个可交付的产物 | Score | code / content |
| **D2 机器可执行性** | 产物能否被运行 / 构建 / 编译 | Score | code |
| **D3 外部消费方** | 产物是否面向会话外的人 / 系统 / 运行环境 | Score | code / content |
| **D4 持久化要求** | 是否要求落盘为文件，而非仅会话内回答 | Score | code / content |
| **D5 句法/语义信号** | 关键词、格式指令、指令强度（「写/生成/实现」vs「你觉得/怎么看」） | Score/Noul | **仅校正，不单独定类** |

> Schema-First 的意义与 P0-3 口径守卫同构：**结构先于生成**。维度固定，判定才可复算、可回溯、可加判据。

### 3.2 三原语在自我判断中的对应

| Jev 原语 | 语义 | 本模块中的角色 |
| --- | --- | --- |
| **Choice** | 从 N 个里选（≤255 选项 + 分布） | 主类判定：`chat / code / content` 三选一 + 校准分布 |
| **Score** | 连续位置 + 置信 | D1–D4 等**正交维度**的连续分（0–1） |
| **Noul** | P(true) 是非判断（**无独立置信字段**） | `ambiguity`（是否模糊/混合）；D5 的句法判断 |

> ⚠️ **Noul 语义陷阱**：`P(true)` 本身就是信念强度，**不要把它当"置信度字段"再套一层阈值**；Score 的等级顺序写反是另一处高频坑。

## 4. 输入输出契约（Contract）

**输入（最小化；判定阶段不取额外上下文）**：

```yaml
request_text:   str          # 用户原始请求
context_hint:   str|null     # 可选：极少量上下文
in_workflow:    bool         # 是否任务中途（决定本次是否真触发）
```

**输出（机器可读，落 `plan.yaml` 的 `meta.入口判定`，与 `meta.决策记录`/`meta.计划修订` 同构）**：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `category` | `chat` \| `code` \| `content` | ✔ | Choice 主类。**枚举唯一取值源见 §1 表** |
| `distribution` | `{chat, code, content}` | ✔ | 校准概率分布，**三键齐全且和 = 1** |
| `confidence` | float 0–1 | ✔ | = `max(distribution)` |
| `dimensions` | `{D1..D5}` | ✔ | 各维 Score/Noul 值 |
| `ambiguity` | bool | ✔ | Noul 判模糊/混合 |
| `route_hint` | str | ✔ | 处理指引（见 §5），非空 |
| `secondary` | `chat` \| `code` \| `content` \| null | — | **可选**：混合请求的次标签 |

**字段化而非散文**，是为了对齐 ai-workflow 既有的"机器可校验"风格（`模型档位`/`自研工具` 等同构）：判定结果可进账本、可回溯、可未来加判据。

## 5. 阈值路由（Threshold Routing）

| 区间 | 行为 |
| --- | --- |
| 主类 `confidence ≥ 0.95` | **自动采信**，进入对应 `route_hint` 路径 |
| `0.70 ≤ confidence < 0.95` | **中置信**：按主类轻量起步 + **标记待复核**，或优先做一次单句澄清 |
| `confidence < 0.70` **或** `ambiguity = true` | **fail-closed**：返回一句澄清问题（triage），**不猜测、不默认走某条路** |

**`route_hint` 按主类给出处理指引（规范后续思考顺序的核心产出）**：

| 主类 | route_hint | 对应任务分层 |
| --- | --- | --- |
| `chat` | 直接答；**不建任务目录、不走阶段 0–6、不落 plan** | L0 |
| `code` | 进 **L2 全流程**；先落 plan.yaml 再动手；关键实现用强模型 + 必要双审 | L2 |
| `content` | 进 **L1/L2**：起草可用 `cheap`/`mid` 档，交付前必须出示验证证据、数值口径一致 | L1 或 L2 |
| 模糊 / 混合 | fail-closed：返回一句澄清问题，不猜测、不默认 | — |

**混合请求**（如「写个脚本生成周报」）：输出 `主类 + secondary`（主 `code` / 次 `content`），由**主类工作流承载**、次类作为其中一个子阶段，**显式拆层**而非含糊合并。

> ⚠️ **`category` → 层级是映射，不是等同**：`code` 基本落 L2，`content` 可 L1 可 L2，`chat` 落 L0（**不落 plan**）。判 `content` 时**不得**据此跳过 L1 模板命中检查——L1 仍需阶段 0 查过 `assets/templates/` 后才能确认。
> ⚠️ **校准优先于准确率**：一个 67% 准确率但**完美校准**的判定器，比 90% 准确率却**错标**的更有路由价值 —— 路由靠的是"概率可信"，不是"猜得准"。这正是下一条阈值取保守值的**理由**（否则会有人问"0.95 凭什么这么高"）。
> ⚠️ **校准未经独立证实前，阈值取保守值**（自动采信 0.95、中置信一律走澄清）——"自信地判错"比"不判"更危险。
> ⚠️ **低置信档刻意不取"转人工 / 升级前沿 LLM"**：该去向出自借鉴文档 §2.3 的**通用**阈值表，它面向"接入快节点的各个门禁"，低置信意味着"**判不了该不该过门禁**"；而本模块低置信只意味着"**没听懂你要什么**"，**澄清一句比升级更轻、也更对症**（与集成方案 §8 一致）。仅当澄清本身需要能力支撑时才升级（接 §6.1 能力路由）。

## 6. 集成位置与机制

self-judge 嵌入主代理的**推理前置**，落点 = **阶段 0 第 1 步之前**：

```
用户请求
  └─► [self-judge 触发] → {category, distribution, confidence, dimensions, ambiguity, route_hint[, secondary]}
        └─► 写入 plan.yaml 的 meta.入口判定   （字段清单以 §4 为准：**6 项必填 + 1 项可选 = 7 字段**）
              └─► 驱动：
                    (a) 任务分层 L0/L1/L2        （取代凭措辞的经验判据）
                    (b) 阶段感知模型路由的初始档位建议
                    (c) 是否进工作流 / 是否需澄清
```

### 6.1 与各组件的协作方式

| 协作对象 | 关系 | 协作方式 |
| --- | --- | --- |
| **任务分层** | 主判据源 | `category` 直接映射 L0/L1/L2（映射关系见 §5）；混合请求显式拆层 |
| **阶段感知模型路由** | 初始信号 | `category` + `confidence` 给初始档位建议（chat→cheap/none；content 起草→mid；code 关键实现→strong）；档位仍写 `plan.yaml` 的 `模型档位` 字段，**保留既有机器校验** |
| **`plan.yaml` / `checks.py plan`** | 留痕载体 | 判定落 `meta.入口判定`；检查项 13 校验（缺失 → WARN，见 §10） |
| **能力路由** | 前置分类 | 先知道是 code 还是 content，再判"缺的是知识/算力/事实/手脚哪一类"，避免无依据引入能力 |
| **入口分型（消息/需求/Bug）** | **并存、正交** | 见 §1.1；Bug 专项闭环不受本模块影响 |
| **`Ledger.md`** | 数据源 | 「入口类型」列改由 `meta.入口判定.category` 提供 |
| **独立审核 / 返修复查 / 熔断 / 反思重试** | **不参与** | 判别层不进入执行期闭环，不与 T1–T3、R1–R6 混用 |
| **红线③ / 出站扫描 / 口径守卫** | **不替代** | 安全关键门禁仍由确定性 AST/代码兜底，见 §8 |

## 7. 判定模型：双 Realization（由谁/什么执行判断）

### 7.1 结论：基础设计**不需要**独立训练的神经网络

self-judge 的目的是"规范模型完成任务的思考顺序"，由**主代理 LLM 自身**在动手前强制执行一次结构化快判即可达成——它直接长在"大脑"里，**无需额外权重**。这是默认 realization。
但同时**必须显式定义"判定模型"**，否则"单次前向、无思维链"只是口号、落不到执行主体。故采用**双 realization**：

| 维度 | **A 脑内协议**（默认） | **B 独立 System 1 模型**（升级） |
| --- | --- | --- |
| 是否新增权重 | 否 | 是 |
| 与"大脑"耦合 | 同源，最贴"集成到大脑" | 解耦，作为外部快判节点 |
| 校准概率 | 间接（纪律 + few-shot 诱导） | 直接（RLCD 式校准目标） |
| 并行 fan-out | 不支持 | 支持 |
| 成本 / 延迟 | 占主模型一次前向 | 极低（厂商自报 **$0.0004 量级、70–500ms 量级**；**未独立复现**，不得作为选型依据引用） |
| 适用规模 | 单请求、低频 | 高频、批量、需解耦 |

### 7.2 Realization A —— 脑内协议（默认，零新增依赖）

- **不是新模型**，而是主代理 LLM 的**自我约束协议**：把 §3 的四步判据写进阶段 0 第 1 步，强制其产出 §4 的结构化判定。
- **"模型"即推理纪律**：判定能力来自 LLM 既有的意图理解，由 schema + §9 判例锚 + fail-closed 兜底诱导出稳定输出；**无单独训练、无单独权重**。
- **诱导目标**：让判定分布尽量"校准"——手段 ① 固定 5 维 schema（防临场发挥）② §9 判例锚定边界 ③ 低置信强制澄清。
- **代价（诚实登记）**：未与执行解耦 → 判定不独立校准、不可并行多问、占用主模型一次前向。

### 7.3 Realization B —— 独立 System 1 决策模型（升级路径）

- **何时启用**：① 高频批量判定 ② 判定与主模型解耦以降成本 ③ 真正并行的 speculative fan-out ④ 独立校准概率驱动阈值路由 —— 此时 A 的前向成本与不可并行成为瓶颈。
- **架构理念（设计层）**：Transformer 一脉，但 decoder 退化为分类/打分头组；选项在 softmax 维度展开；核心是 hardware-aware 并行采样器，一次前向并行产出 D1–D5 的 Score/Noul + Choice 分布。
- **训练理念（设计层）**：RLCD 式校准目标（优化 Brier Score 等评分规则，使"说 p 置信 ≈ p 情况对"），数据用**纯合成**生成"意图态 → 判定对"配对。
- **本地落地**：官方 Jev API **未向中国大陆开放**，不直连；若启用 B 走社区复现（OpenJev 冻结 Qwen3.5-4B + 受限 softmax；APUS `fast-browser-use`，MIT）。
- **接口**：与 §4 **完全一致**，故 A ↔ B 切换对下游透明。

> **落地顺序**：先上 A（零新增依赖、立刻可用），出现 §7.3 所列瓶颈再升级 B；**契约不变**。

## 8. 不可委派与护栏

- **不授权写操作**：只输出"这是什么"，**不输出"我可以做"**。工作区边界红线、写操作确认仍归确定性规则与人工。
- **不替代安全关键门禁**：红线③越界判定（`_check_scope`）、出站扫描（`scripts/outbound_scan.py`）、口径守卫（`_check_parity`）保留 AST/代码实现，self-judge 仅作辅助信号。
- **不越界**：判定只读用户请求文本，**不读全库、不触发重检索**。
- **不进入执行期闭环**：不参与独立审核、返修复查、熔断判定、反思重试。
- **理由**：概率校准尚未独立证实、且**可在 schema 内高置信选错**；安全/不可逆动作不能押在 unverified 模型上。

## 9. 判定样例锚（边界判例，供 Realization A 的 few-shot 锚定）

> 作用：把"chat/code/content 的边界在哪"锚成**可复用的判例**，而不是每次临场发挥。列 5 条种子判例，首次使用后可继续追加。

| # | 请求 | 主类 | 关键判据 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | 「解释一下什么是 KV 缓存」 | `chat` | D1=0（无交付物）、D4=0（不需落盘） | 高置信 |
| 2 | 「帮我写个脚本，把这三份 CSV 合并成一份」 | `code` | D2=1（产物可运行）、D4=1 | 高置信 |
| 3 | 「整理一份 Q3 竞品分析报告」 | `content` | D1=1、D2=0、D3=1、D4=1 | 落 L1 或 L2（视复杂度） |
| 4 | 「写个脚本生成周报」 | `code` + `secondary=content` | 主类由 D2 决定，`secondary` 显式拆层 | **混合请求**：主类承载、次类作子阶段 |
| 5 | 「看看这个数据，你觉得有什么问题」 | 判 **`ambiguity=true`** | 无明确交付物形态、D1 居中 | **fail-closed**：提一句澄清（要口头结论，还是要一份分析文件？） |

**判例 5 是重点**：它不是"判不出来所以要猜"，而是"**判不出来所以要问**"。fail-closed 的产出是**一句澄清问题**，不是一次冒险归类。

## 10. 诚实边界与验收

沿用本技能一贯的"诚实边界"风格：**写在提示里的门禁不是门禁**。

1. ⚠️ **校准不可机器强制** —— `confidence` 由模型自填，**无法被工具证明"真的校准"**。它是**纪律 + 留痕项，不是门禁**。任何"已由工具保证校准"的说法都不成立。
2. ⚠️ **缺失 `meta.入口判定` 不是 FAIL，是 WARN** —— `checks.py plan` 检查项 13 的口径：整段缺省 → **WARN**（向后兼容旧 plan，**不追认历史计划**）；一旦填写，结构非法 → **FAIL**（沿用"可选字段、填了就不能糊弄"）。**不得宣称该字段是强制门禁。**
   - ⚠️ **此处相对理念层 §2.1 有一处刻意收敛**：理念层写"判定缺失则整个动作**不得启动**（fail-closed）"；本技能**不为此造机器门禁**（与集成方案 §11「未来加判据…**不造门禁**」一致）。"必触发"由 **§2 的纪律层**承担，机器只做提示 —— 理由同 §10.1：校准未证实前，把纪律伪装成门禁会造出假安全感。
3. ⚠️ **判定也会判错** —— 下游必须可观测、可复核；判定结果随请求留痕（`meta.入口判定`），便于回检"当时为什么归到这类"。
4. ⚠️ **类型合法 ≠ 判断正确** —— 本模块保证输出**落在 chat/code/content 之一**（零类型错误，Jev"零幻觉=类型安全"的边界重述），**不保证类别选对**。区分"结构合法"与"判断正确"两层，正是 `checks.py plan` 第 11 项曾三次被误读成绿的根因。
5. ⚠️ **判错比不判更危险** —— 故低置信一律降级到"问一句"（fail-closed），自动采信阈值取保守值 0.95。

**验收信号（可判定）**：

| 信号 | 判定方式 |
| --- | --- |
| 进入工作流的请求，其 `plan.yaml` 含 `meta.入口判定` 且 `category ∈ {chat, code, content}` | 机器（`checks.py plan` 检查项 13） |
| 模糊请求**确实**走了澄清而非默认分类 | 人审（查 `meta.入口判定.ambiguity` 与对话留痕） |
| 抽样 **20 条**历史请求，分类与人工复核一致率 | **人审**（未证实前只报"**一致率**"，**不声称"准确率"**；一致率的合格阈值本身仍标"约定阈值"，本版**未定值**） |
| 声明块（`references/self-judge.md` §1，一对 ASCII 标记圈定）取值 ↔ 代码常量同源；**块须在源规格面内恰一处**且块形合法（含「首格整格一个裸词」） | 机器（`checks.py skill`：`口径守卫：入口判定主类`的**确定性**那一半） |
| 源规格面内「主类疑似列」（连续表格行、按**列**裸词占比判定）未出现未登记取值 | 机器 **WARN**（`checks.py skill`：`口径守卫：入口判定主类扫描（启发式·WARN）`，**只提示不阻断**） |
