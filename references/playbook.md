# 项目差异化流程手册（阶段 3 按需加载）

> 通用六阶段对所有任务生效；本文件只记录**各项目类型的额外要求**。
> 状态：v1（2026-09-10 建立）。实际跑过后请按阶段 6 复盘结果更新。

---

## 一、量化分析 / 交易系统类

> **通用数据分析类任务也参照本节**——数据完整性三查、对账差额、空值率报告是同族验证信号；未列出的任务类型可照此归纳验收信号（并在完成后回填本节或 `quality-gates.md` 信号表）。

**典型任务**：策略回测、因子分析、数据清洗、指标计算、风控规则实现。

额外要求：
1. **验收信号必须可数值化**：回测收益/回撤/夏普、因子 IC/IR、对账差额（如"持仓市值 = 现金 + 证券市值，误差 = 0"）。禁止用"看起来对"验收。
2. **数据完整性三查**：行数一致、时间戳连续无缺口、空值率报告；停牌/除权除息必须显式处理，不得静默前向填充。
3. **前视偏差（look-ahead bias）自查**：任何用到未来信息的字段必须列出并说明处理方式——量化类最常见的致命错误。
4. **资金/交易/权限代码禁止纯 AI 生成**，必须人工逐行复核（见 `quality-gates.md` 第三节红线）。
5. **性能与并发属性测试**：N+1 查询计数（每请求 >15 告警）、`hypothesis` 不变量测试（如 `balance >= 0`）——AI 常写出"10 行数据没问题、1 万行就死"的代码。
6. 交付物默认 Markdown 报告 + 必要 CSV/xlsx；图表用红涨绿跌（中国市场惯例）。

## 二、跨境电商智能选品类

**典型任务**：多源数据融合、竞品分析、需求/利润率测算、选品决策表。

额外要求：
1. **数据源台账**：每个字段标明来源、抓取时间、口径；不同源的同名字段必须明确换算规则（汇率、含税、单位）。
2. **口径一致性校验**：跨源聚合前先抽样对账（抽 10 条人工核验），否则"融合"只是数字堆叠。
3. **决策可解释**：选品结论必须给出权重与阈值来源，禁止黑箱打分；分档输出（强烈推荐/观察/淘汰）+ 每条理由。
4. **抓取合规**：遵守目标站点 robots 与频率限制；抓取脚本必须带限速与重试（可直接复用 `scripts/http_fetch.py` 的退避逻辑）。
5. 输出 Excel 选品表（含评分列与筛选条件）+ Markdown 分析报告。

## 三、网络小说写作类

**典型任务**：开新书、日更章节、大纲/设定维护、市场选题分析。

额外要求（**流程固化，逐项打勾**）：
1. **写作前必读检查清单**：前 5 章原文 + 大纲 + 设定锚点 + 章标题登记表（防重复）。
2. **章节规格**：每章 2000-2400 字（番茄平台口径）；日更目标 2000 字；存稿 2.5-3 万字再申签。
3. **10 项自查**：爽点轮换、章末两层钩子（悬念 + 期待）、设定锚点、前文承接、人物行为一致、对话占比、节奏（无流水账）、无 AI 腔、合规检查、标题查重。
4. **合规底线**：涉政/涉黄/涉暴/迷信等敏感内容零容忍；主角行为须符合平台价值观。
5. **反 AI 味**：禁止"总之/综上/值得注意的是"等书面语与四字排比堆砌；段落长短交错；避免每章结构雷同。
6. 交付物：MD（写作底稿）+ Word（投稿/存档）双格式；章节文件命名固定为 `第NNN章-标题.md`。

## 四、学习资料生成类

**典型任务**：复习讲义（PDF）、知识总结（HTML）、题库、学习路径规划。

额外要求：
1. **知识锚点可溯**：每条结论标教材章节/论文出处；公式给出推导关键步而非只给结果。
2. **分层输出**：一页速览（结论+公式表）→ 详解（推导+例题）→ 自测题（含答案与解析），适配不同复习阶段。
3. **数学/理工内容**：公式用 LaTeX 渲染（HTML 侧 KaTeX/MathJax），PDF 侧避免字体缺失导致公式乱码。
4. **自测题必须有答案与解析**，且题目数量与知识点覆盖度对齐（每个知识点 ≥1 题）。
5. 交付物：PDF（复习用）+ HTML（交互/速查用）；HTML 单文件自包含、离线可开。
6. **禁止幻觉**：不确定的定义/定理必须标注"待核实"或先去检索确认，不得编造公式。

## 五、缺陷修复类（Bug 入口，阶段 0 分型为 Bug 时必读）

**铁律：未复现不得动手改。** 顺序固定为「复现 → 根因 → 修复 → 回归」，缺一步即视为未完成。

1. **复现**：先取得可重复的失败现象（命令 + 输入 + 完整报错/截图 + 环境），记录为「复现步骤」。复现不了 → 只做只读调查并向用户要更多信息，**禁止凭猜测改代码**。
2. **根因定位**：从报错栈/日志往下钻到**触发条件与责任代码**；区分「现象点」与「根因点」（如"输出乱码"的根因常在编码写入处，不在打印处）。用 `ast-grep` 查调用链，用 `Grep` 找同类写法（**同一根因往往有 N 处，只修一处就叫没修完**）。
3. **影响面**：列出谁会受影响（调用方、数据、下游产物、已交付报告），标出**不可逆影响**（已发布内容、已被引用的数据）。
4. **修复**：最小改动优先；不得顺手重构无关代码（会把 Bug 修复变成不可控改造）。改动点写入 plan.yaml。
5. **回归验证**（双条件，缺一不可）：
   - 原失败用例**转为通过**（贴出前后输出对比）；
   - 相关的原有验证信号**仍通过**（防"修好这个、弄坏那个"）；
   - 若根因存在多处同类写法，逐处确认或显式登记"其余 N 处未修 + 原因"。
6. **交付**：说明「根因 + 改动点 + 回归证据 + 遗留风险」；修不动或属外部依赖问题，明确说清而不假装修好。
