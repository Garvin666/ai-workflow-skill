## 自研工具与技能：标注与公开留痕（贯穿阶段 3–6，v3.1.0 新增）

> **起因（用户 2026-09-15 指定）**：任务中常需自写脚本/技能补齐能力缺口（能力路由的「手脚」类）。这类产物**既不是第三方依赖、也不是用户既有资产**——若不声明来源、不公开留痕，事后无人知道它是什么、从哪来、还能不能用；更糟的是它会被当成成熟库而承担不该有的信任。

### 判定：什么算「自研」

同时满足两条即命中：① **本任务（或本技能）自行编写**，非复用/克隆第三方、非用户既有资产；② **以文件形式落地**——脚本（`.py`/`.ps1`/`.sh`）、技能包（`SKILL.md` + 配套文件）、模板、配置生成器等。

**不算自研**（不触发）：未落盘的一次性内联命令、对既有文件的局部修改、第三方项目的 fork 改造（仍走阶段 2 引入前检查，并注明上游来源与许可证）。

### 三条硬要求

| # | 要求 | 落在哪 | 可判定信号 |
| --- | --- | --- | --- |
| 1 | **代码内标注**：自研标识 / **名称** / **用途** / **适用场景** / 仓库链接，五项齐全 | 脚本＝文件头注释块；技能包＝`SKILL.md` frontmatter + 正文首段 | 该文件头部 `grep` 命中 `[自研` |
| 2 | **输出中标注**：交付说明、报告、`Ledger.md` 凡引用该工具处，须出现「自研」+ 名称 + 仓库链接 | 交付说明 / 报告 / 台账 | 人审：产物里能直接看到三者 |
| 3 | **同步推送 public 仓库**：完整源码推送到公开仓库；**首次创建后每次新增/修改都要及时推送，保持版本一致** | `scripts/publish_tools.py` | `publish_tools.py verify` 报 `public=true` 且远端 blob sha 与本地一致 |

**禁止**：把自研产出写得像成熟第三方库（不标来源、只给工具名不给链接）；把尚未推送的本地脚本当既有能力引用。

### 标注模板

脚本**文件最前面**的注释块：

```text
# [自研工具] <名称>
# 用途：<一句话，它做什么>
# 适用场景：<什么情况该用它；什么情况不该用>
# 作者：ai-workflow 自研（<任务名> <YYYY-MM-DD>）
# 仓库：<repo_url>/blob/main/<path>　← 推送后回填；未推送前写「待推送」
```

技能包：`SKILL.md` frontmatter 加 `selfbuilt: true` 与 `repo: <url>`，正文首段给出用途 + 适用场景。

### 仓库与推送工具

- **默认仓库**：`https://github.com/Garvin666/ai-workflow-tools`（**public**，放**自研工具**源码）。覆盖方式：`SELFTOOL_REPO` 环境变量，或 `publish_tools.py --repo OWNER/NAME`。
- **两仓分工（用户 2026-09-16 定）**：**自研工具** → `ai-workflow-tools`；**技能本体** → `Garvin666/ai-workflow-skill`（本技能自身即自研技能，已在 frontmatter 标 `selfbuilt: true` + `repo:`，正文首段给出用途／适用场景／链接）。推送技能本体用 `--repo Garvin666/ai-workflow-skill`。
- **`scripts/publish_tools.py init --name <仓库名> [--apply]`**：创建 **public** 仓库（本规则不允许 private，故无 `--private`）；默认 dry-run。**幂等**：仓库已存在且为 public → 打印 `[OK] …跳过创建（幂等）` 且退出码 0；已存在但为 private → FAIL 并给出改可见性指引。
- **`scripts/publish_tools.py push --file <本地路径> [--dest <仓内路径>] [--message …]`**：默认 **dry-run**（只打印将写入的仓内路径与 blob sha），加 `--apply` 才真写；已存在文件带远端 `sha` 更新，**幂等可重跑**（内容一致则 `[SKIP] … 一致，无需推送`）。
- **`publish_tools.py verify [--file …]`**：查仓库 `private` 字段（**为 true 直接 FAIL——规则要求 public**）+ 比对远端 blob sha 与本地是否一致。**这是"版本一致"的机器判据**，不靠"我记得推过了"。
- 网络口径：一律走 `api.github.com`（本机 `github.com` 主域间歇不通）；凭据优先级 `--token` → `GITHUB_TOKEN` → `GH_TOKEN` → `gh auth token`，**只读不落盘、不打印完整值**（全局凭据纪律见 `references/security-guide.md`，此处不再另立口径）。
- ⚠️ **创建仓库与首次推送属不可逆对外动作**，须按阶段 2 第 7 条**单独取得用户确认**后再执行，并按阶段 5 第 8 条**附内容清单与可见性**（public 判定须在确认时显式写明）。

### 两类资源的分流推送路由（v3.2.0，用户 2026-09-16 指定）

> **分工**：本体（Ontology）→ `ai-workflow-skill`；自研工具 → `ai-workflow-tools`。
> **一条命令**：`python scripts/push_router.py push --base <rev> --head <rev> [--apply]`（**默认 dry-run**）。
> **推完必验**：`python scripts/verify_push.py --rev HEAD --prev-remote <推送前远端 HEAD>`（见 ⑤）。
> ⚠️ **最容易误解的一点：分流不是互斥二选一。** 本体 ＝ 技能仓改动面的**全量**（技能本体 + 任务档案）；自研工具 ＝ 其中的**子集**。所以 `scripts/` 下的自研脚本属**双属** —— 既作为本体快照进技能仓，又作为独立工具进工具仓，两条通道各推一份（内容同源；同一文件在两仓的 blob sha 相同，这本身就是「版本一致」的天然证据）。

#### ① 触发条件

| 改动类型 | 本体通道（→ 技能仓） | 自研工具通道（→ 工具仓） |
| --- | --- | --- |
| 新增 A | 推 | 推（仅当判定为自研工具） |
| 更新 M | 推；内容一致则幂等跳过 | 推；同上 |
| 重命名 R | 按「删旧 + 增新」 | 新路径更新；旧路径删除须 `--allow-delete` |
| 删除 D | **默认只列出、不执行**，须显式 `--allow-delete` | **不自动删**（避免误删公开产物，需网页人工删） |
| 无变化 | `[=] … 同内容跳过` | `[SKIP] … 一致，无需推送` |

**推送时点**：阶段 6 沉淀 —— 与「首次创建后每次新增/修改都要及时推送、保持版本一致」同一条要求。

#### ② 判定依据（标注头 + 登记表交叉校验）

| 维度 | 判据 |
| --- | --- |
| **本体** | 路径落在技能仓内（技能本体 + 任务档案）。`git diff` 的文件名即判据 |
| **自研工具** | 三条**同时**满足：① **事实**——文件首部含 `[自研工具]`/`[自研技能]` 标注块（脚本），或 `SKILL.md` frontmatter 含 `selfbuilt: true`（技能包）；② **意图**——任意 `tasks/**/plan.yaml` 的 `meta.自研工具` 有对应登记项；③ **指向**——该登记项的仓库链接指向**工具仓** |

**交叉校验（不一致即 FAIL，且阻塞推送）**：

| 情形 | 判定 |
| --- | --- |
| 有标注头，但登记表无此项 → **漏登记** | FAIL（用 `checks.py selftool` 补登记） |
| 登记项可映射到该文件，但该文件无标注头 → **登记与实现不符** | FAIL |
| 有标注头且已登记，但链接指向**本体仓**（技能本体自身即如此） | OK —— 只走本体通道，不推工具仓 |
| 标注头缺「名称 / 用途 / 适用场景 / 仓库」任一项 | FAIL |
| 登记项未涉及本次改动面 | SKIP（历史登记或本次未改动，非错误） |
| 文件在技能根之外 | WARN —— 不归本分流器管辖，直接用 `publish_tools.py` |

#### ③ 推送格式（两条通道形态不同，由分流器包装）

| | 本体通道 | 自研工具通道 |
| --- | --- | --- |
| 脚本 | `scripts/push_ontology.py` | `scripts/publish_tools.py push` |
| API | Git Data API：blob → tree（带 `base_tree`）→ commit → PATCH ref | contents API：单文件 PUT |
| 粒度 | 一次 commit 覆盖本次全部改动 | **逐文件**，每文件一次提交 |
| 换行符口径 | 取 `git cat-file blob`（git 对象库天然 LF） | CRLF→LF **归一化后**再算 sha |
| 仓内路径 | ＝ 相对技能根路径（与本地一致） | ＝ 相对技能根路径（同一规则） |
| 删除 | 支持（需 `--allow-delete`） | 不支持（人工在网页删） |
| 理由 | 远端是**混合仓**且其历史由 API 创建、与本地不互通 → `git push` 会被拒 | 工具仓是纯净单文件仓，contents API 足够 |

#### ④ 冲突处理策略

| 冲突 | 策略 |
| --- | --- |
| 内容已一致（重复推送） | **幂等跳过**，可反复重跑 |
| 远端被并发推送 | 本体通道的 commit parent 取远端**当前** HEAD，且 `PATCH ref` 用 `force=false` → 非快进即失败；另可用 `--expect-remote <sha>` 显式锁基线 |
| 新建 blob 的 sha 与远端返回不符 | **立即抛错**（换行符/编码口径问题的机器判据，绝不静默改写） |
| 混合仓中远端独有项（工作区档案侧） | **永不因本次推送被删** |
| 删除项 | 默认只列出待删；须显式 `--allow-delete` |
| 交叉校验 FAIL | **阻塞两条通道** —— 不推半截 |
| 本体通道失败 | **中止**，不再继续工具通道（避免半推送状态扩大） |
| **工作区有未提交改动** | **阻塞推送**（须显式 `--allow-dirty` 才放行）—— 本体通道按 **commit 内容**推、工具通道按 **工作区文件**推；两者不同源时，同一文件在两仓 blob sha 会不一致、公开仓可能躺着已修好的 bug 的旧版本。**这条是实测踩出来的**：v3.2.0 首轮推送时一处修复发生在 commit 之后，两仓内容一度不同（见 `Ledger.md`）。 |
| 登记项与技能包的映射 | 用 frontmatter `repo` 与登记链接**同仓比对**，**不**依赖名称里是否含中文关键词（那种判据一改命名就失效） |
| **`--result-file` 落盘失败** | **只 WARN，绝不改变推送结论**；相对路径以**技能根**为基准解析（不随 cwd 走），且越出技能根的路径**拒绝写入**。**这条是实测事故推出来的**：分流器用 `cwd=scripts/` 调通道，相对路径被写到 `scripts/tasks/…`（父目录不存在）→ 在**推送已成功之后**抛异常 → 退出码 1 → 一次成功的推送被日志路径掩盖成失败，工具通道还被顺带中止（见 `references/changelog.md` v3.2.1 条目）。 |
| ⚠️ **已知边界**（如实登记，不假装有保护） | 无跨会话基线时，**无法检测「远端被第三方改写」**这类漂移；如需该保护，推送后记录 sha 并用 `--expect-remote` 显式约束 |

#### ⑤ 推送后的独立验收（v3.2.1，把验收器正式化）

**命令**：`python scripts/verify_push.py --rev HEAD --prev-remote <推送前的远端 HEAD> [--expect-remote <推送后远端 HEAD>]`

调用方只需给两件事：**本地 rev** 与**推送前远端 HEAD**。期望版本号从本地 rev 的 `SKILL.md`
**自动推导**，自研工具清单从 `tasks/**/plan.yaml` 的 `meta.自研工具` **自动发现**，默认分支从远端
元数据取 —— 刻意消灭所有"人工记得改"的常量（旧做法是每轮复制一份再手改常量，而"复制粘贴漏改"
恰是作者自查最抓不住的一类错）。

| # | 判据 | 判 FAIL 的典型情形 |
| --- | --- | --- |
| 0 | 工作区干净 + rev 可解析 | 有未提交改动（登记表读的是工作区，可能与已推送版本不同步） |
| 1 | 远端 HEAD == 期望；≠ 推送前值 | 推送根本没发生（空跑） |
| 2 | 本地 rev **⊆** 远端，且同名文件 blob sha 逐一相等 | 漏推文件、推了旧内容（sha 不同） |
| 3 | 远端独有项均由**推送前** base_tree 证明早于本次推送；远端 blob 数未减少 | 本次意外新增/删除了远端文件 |
| 4 | 每个自研工具在工具仓的 sha == 本地**独立重算**值 | 登记为已推送但远端没有该文件；工具仓是旧版本 |
| 5 | 远端 `SKILL.md` 版本 == 期望，且含 `selfbuilt` + **指向 `references/push-routing.md` 与 `references/changelog.md` 的指针**；远端 `references/push-routing.md` 可取且含分流小节/触发条件/判定依据/冲突处理/独立验收 | 文档没推上去、版本号没对齐、**或指针指向了不存在的新家（断链）** |
| 6 | **跨仓一致性**：同一文件在技能仓与工具仓 sha 必须相同 | 两仓内容不同源（公开仓可能在放旧版本）—— 被真实事故推出来的判据 |
| 7 | 两仓均为 public | 可见性被改（规则不允许 private） |

**为什么单独写一个脚本、且与推送脚本零代码共享**：用推送脚本自己的逻辑验推送结果，只能证明
「它自洽」，不能证明「它对」。本脚本自己算 blob sha（`sha1("blob <len>\0" + data)`）、自己经
api.github.com 取远端、自己解析本地 tree。它还与 `push_router.py` 构成**方向相反的第二实现**
—— 分流器是「标注头驱动」（先扫文件、再回查登记），验收器是「登记表驱动」（先读登记、再回查
文件）；两者同时通过才算交叉印证。

**几种"看起来像失败、其实不是"的情形**（都会显式标 SKIP 或说明，不静默）：
未传 `--prev-remote` → 判据 3 判 SKIP（无法机器证明，需人工确认）；登记项链接为「待推送」→ SKIP；
登记项对应的文件只在工作区、未入版本控制（测试替身/中间产物）→ SKIP；`tasks/*/tmp/` 下的
plan.yaml **不读**（那里是探针伪造的假登记）。
**推送后未验收 = 阶段 6 未完成**：`Ledger.md` 的交付物列须附验收结论（FAIL 数）。

### 推送后的独立验收：多通道口径与两条结构性限制（v3.4.0 实测）

`verify_push.py` 的判据 3 建于一个**建模前提**上：**一轮推送 = 一个本地仓 + 一次提交**。
而 `ai-workflow-skill` 是**混合仓**，一轮里可能有两条本地来源：

| 通道 | 本地 git 根 | 工具 | 改动面来源 |
| --- | --- | --- | --- |
| 本体通道 | 技能根 | `push_ontology.py`（经 `push_router push`） | 技能仓的 rev 区间 |
| 工作区档案通道 | 工作区根 | `push_ontology.py --root <工作区>` | 工作区仓的 rev 区间 |
| 工具仓通道 | 技能根 | `publish_tools.py` | 工作区**文件**（非 rev） |

**口径：按通道分跑，一通道一次。** 每次 `--prev-remote` 取**该通道推送前**的远端 HEAD，
`--skill-dir` 指向**该通道的本地 git 根**（v3.4.0 起它同时是本地 git 根，见 `ops.md`）。

**为什么不能只跑一次（实测，不是推理）**：判据 3 把「在远端、不在本地 rev 内、且不在推送前 tree 里」
的路径一律判为新出现。于是 —— **后推送的通道**用自己推送前的基线能全绿（它的新增项确实在自己的 local rev 里）；
**先推送的通道**若等到兄弟通道推完才复核，就必然把兄弟通道的新增项报出来（本轮实测 6 项 = 工作区通道推的 6 份报告）。
反过来若改用更晚的基线（`--prev-remote` 指到本通道推送**之后**），判据 1 的「非空跑」又会 FAIL ——
**不存在单次全绿的基线**。这是前提不成立，**不得靠放松判据掩盖**，也不应把文件挪来挪去以求一次全绿。

**限制一：`.gitignore` 在同一远端路径上撞车（2026-09-17 已按修法 ② 解决）**。两条本地来源各有自己的
`.gitignore`，且**策略相反** —— 技能仓要忽略 `tasks/*/plan.yaml`、`tasks/*/tmp/`，工作区仓要**跟踪**它的
`tasks/*/plan.yaml`。远端只存一份 → **后推者覆盖先推者**，另一侧的判据 2 恒 FAIL
（实测：本地 `5138ffeea1` ≠ 远端 `3d53038d4d`；远端当时为技能侧版本，未被覆盖）。

> ⚠️ **本节此前的状态标注已作废**（原文见本仓 git 历史，以及
> `tasks/修复-gitignore同路径撞车-2026-09-17/口径更新待办.md` 对其的逐字引用）。
> **不要依据那些旧引用判断现状。**

**已落地修法（修法 ②：工作区侧弃权）**：工作区仓 `git rm --cached .gitignore` 并本地提交
（`7011bf0` → `8fb80fc`，2026-09-17，18 行删除）；原有忽略规则**逐条迁入 `.git/info/exclude`**
（并追加 `.gitignore` 自身，见该文件 `:35`）。`.gitignore` 文件保留在磁盘上（206 B，非破坏性），仅退出跟踪。
