# 检索快判（retrieval-judge，v4.5.0 新增）

> **定位**：ai-workflow 在**每一次实际检索之前**必跑的一个 **System 1 结构化判别**模块——动手查之前先判一次「该不该查、查哪一类源、查到什么程度算够、能不能下『不存在』的断言」，据此规范后续「查什么、查多深」。它是 `self-judge`（入口级：判"这是什么任务"）与 `method-judge`（步骤级：判"这一步用什么手段"）的**检索级第三块拼图**：self-judge 决定走哪条路，method-judge 决定每步踩哪块砖，本模块决定**每块砖下面的土往哪里挖、挖多深**。
> **它是红绿灯，不是车**：只输出「信息该从哪来、够不够、能不能断言」，不产出具、不授权、不越界、不替代安全关键门禁。
> **配套（机器侧随 v4.5.0 一同新增）**：判定结果**逐条追加**到 `assets/plan-template.yaml` 的 `meta.检索判定` 列表（每次检索一条，与 `meta.方法选用` 同构）；机器校验见 `scripts/checks.py plan` 检查项 16 与 17。
>
> ⚠️ **哲学来源**：Jev（TypeSafe AI 的 System One 模型）三原语 Choice / Score / Noul + 校准概率 + fail-closed + 判定即结构。设计依据为**前两个 judge 的契约本身**（`self-judge.md` / `method-judge.md`，二者均声明其设计依据为工作区三份 JEV 设计文档：理念层 / 集成方案 / 借鉴清单）。
> ⚠️ **不做落地层（明确约束）**：与 self-judge / method-judge 同，**默认 Realization A（脑内协议）**——由主代理 LLM 自我约束产出结构化判定，**不训独立决策模型**。沿用 method-judge §7.3 的既定路线「**只上 A**」，不新开路线。

## 1. 定位与形态

| 项 | 值 |
| --- | --- |
| **模块名** | `retrieval-judge`（中文：**检索 · 快判**） |
| **形态** | ai-workflow 的**内部子模块**（非独立顶层 skill）；本文件即其完整契约，由阶段 3 第 5 条（精确检索）之前加载 |
| **本质** | 纯判别（System 1）：**单次前向、无 chain-of-thought、无自回归展开** |
| **主语** | "模型给自己该查什么做判断"——判的是「**这一步的信息缺口该用什么源补、补到什么程度**」，不是"我能不能查" |

**源类（Choice，五类）**：

| 类 | 含义 | 典型手段 |
| --- | --- | --- |
| **本地资产** | 工作区内的源码 / 配置 / 产物 / 数据文件 | `Grep` / `Glob` / `Read` / `ast-grep` / `data_query.py` |
| **历史留痕** | 本工作区既往任务的计划、结论、踩坑与台账 | `tasks/**/plan.yaml`、`Ledger.md`、`trace.jsonl`、`memory/` |
| **知识库** | 个人知识库（KB-First，离线语义检索） | `kb.py retrieve` |
| **技能手册** | 已装技能的指令与手册（判"有没有现成能力"） | 技能索引 `README.md`、`skills/*/SKILL.md`、`references/*.md` |
| **联网** | 本机推不出的当世事实 / 外部数据 | `http_fetch.py` / GitHub API / 网页检索 |

> 本模块的 **`source_class` 取值域就是上表五类**（可组合，如 `本地资产+联网`）；**不另造一套**。上表的工具清单由 `SKILL.md` 阶段 3 第 5 条与阶段 1 第 1 条持有，本模块只做"按该清单出结构化判定"，二者**判据同源、职责正交**（沿用「技能库卫生」第 4 条）。
> ⚠️ **五类是封闭枚举，不是示例**。未命中任何一类时应判 `needs_retrieval=false` 或走 fail-closed 澄清，**不得**新增第六类 —— Jev 的 answer space 前提是「高度可枚举」，开放列表会让受限 softmax 与校准同时失效。

### 1.1 与「精确检索」「方法选用」的关系（**三层正交，不是替换**）

⚠️ **这是一处刻意收敛，理由写在下面，请勿当成笔误。**

三个 judge 各自盯一根**不同的轴**，任何两者都不可互相推导：

| 模块 | 轴 | 回答的问题 | 落盘位置 | 决定的后果 |
| --- | --- | --- | --- | --- |
| **self-judge**（入口级） | 认知轴 | 这次要我**产出什么**？ | `meta.入口判定` | 任务分层、模型初始档位、是否落 plan |
| **method-judge**（步骤级） | 手段轴 | 这一步该用**什么工具/方法**？ | `meta.方法选用` | 引入哪类能力、选哪个工具 |
| **retrieval-judge**（检索级） | **信息轴** | 这一步的信息**从哪来、查到什么程度算够、能不能断言"没有"**？ | `meta.检索判定` | 查哪类源、查多深、**能否下否定断言** |

> ⚠️ **时点注记（2026-09-23，v4.7.0）**：上表**已扩为四行** —— 新增**结构级**的 `homework-judge`
> （判「要不要按作业模式 H1–H5 作答」，落 `meta.作业判定`，契约见 `references/homework-judge.md`）。
> 上文「三个 judge」「第三块拼图」等表述是 **v4.5.0 时点的原话，按「不删原文」保留**；
> 四块的分工以 `references/homework-judge.md` 附录 A 为准。

**为什么不能合并进 method-judge**：method-judge 的 `gap_class=事实` 只回答"该联网"，它**不回答**「联网查什么、查到什么程度算够、查不到时该怎么表述」。实测中最常见的失效恰恰落在后三项——模型联网搜了一轮没搜到，就直接对用户说"这个不存在"，而它**既没说查了哪些源，也没说还有哪些源没查**。这属于信息轴，不属于手段轴。

**为什么不能合并进 self-judge**：self-judge 只作用于**任务入口**且明确"不作用于执行期子步"（其 §2），而检索决策在**每一步**都会发生。

> 即：`SKILL.md` 阶段 3 第 5 条告诉你"网页用 `http_fetch`、本地目录用 `Grep`、结构用 `ast-grep`"；`retrieval-judge` 在每次检索前把"我这次判为**本地资产**类、候选 `src/deck/themes/`(fit 0.95) / `README.md`(fit 0.60)、needs_retrieval=true、confidence=0.96"落成结构，并在查不到时**强制区分**「已查 A/B/C，0 命中」与「未查 D/E」。**判据在手册，判定在契约**——这正是 self-judge 与入口分型「两层正交」的同构处理。

## 2. 触发条件

| 场景 | 是否触发 | 说明 |
| --- | --- | --- |
| 阶段 3 任一步骤**需要获取信息**（绝大多数步骤） | **必触发** | 取代"凭印象随手查/随手断言" |
| 纯内联推理、所需信息已全部在上下文中 | **触发但可秒达** | `needs_retrieval=false` 即结论；**为留痕仍跑一次**，但不必写决策记录 |
| 已在子代理内部 | **不触发** | 本模块作用于主代理的检索决策，不混入子代理内部 |
| 用户明示「直接做 / 别走流程」 | **触发后遵从授权** | 判定留痕供回溯，不改变用户授权语义 |
| **即将下"不存在 / 没有 X / 未使用 Y"这类否定断言** | **必触发且强制留痕** | 这是本模块存在的主要理由，见 §5 |

**主动克制（判定阶段禁止做的事）**：**不触发真检索、不读全库、不派子代理、不展开思维链**——否则就退化成 System 2，失去"快"的意义，也违背"先判后查"的次序。输入只需本步的「需要什么信息 / 已有线索 / 工作区根」三字段。

## 3. 执行步骤（单次前向、四步、无自回归）

```
① 解析 ：本步所需信息 + 已有线索 → 结构化信息缺口态  —— 不触发真检索
② 评估 ：并行打分 5 个正交维度 R1–R5 → 各维 Score(0–1) 或 Noul(P(true))
③ 选择 ：Choice 源类（五类，可组合）+ 该类下候选检索目标及 fit_score
④ 二值 ：Noul 判定「needs_retrieval」→ 输出结构化判定
```

四步**全为单次前向**。第③④步共用同一次判别，不得为"提高准确率"而多次采样（Realization A 下多次采样即多付一次前向；Realization B 才允许并行 fan-out，见 §7）。

### 3.1 判定维度 Schema（Schema-First：先定义维度，再判定，固定不临时发挥）

| 维度 | 含义 | 原语 | 高分指向 |
| --- | --- | --- | --- |
| **R1 信息缺口** | 本步所需信息，模型既有知识 + 当前上下文是否已足够 | Score | 缺口大 → **必须检索** |
| **R2 本机可得性** | 所需信息是否在**工作区内**已有（`Grep`/`Read` 够不够） | Score | 本地资产（**反向指针**：高分＝不必联网） |
| **R3 留痕可复用性** | 是否已有同类任务的计划 / 结论 / 踩坑可直接复用 | Score | 历史留痕 |
| **R4 外部时效性** | 是否依赖**当世事实**（训练数据可能过期或本机推不出） | Score | 联网 |
| **R5 候选池纯净度** | 目标源内**噪声占比**（无关项会不会稀释注意力） | Score | **反向指针**：低分＝必须先清洗 / 分层 |

> R1–R4 是**语义维度**，决定源类；R5 是**校正指针**，只决定"要不要先清洗候选池"，不单独定类（与 self-judge 的 D5、method-judge 的 M5 同构）。

**候选池清洗（R5 低分时的强制动作，源自 Jev 的「无关项干扰」失败模式）**：以下路径**默认排除**，除非本步目标就是它们 —— `node_modules/`、`dist/`、`build/`、`.venv/`、`_archive/`、`.git/`、第三方参考目录（如本工作区的 `gods-eye-view/`）、二进制与锁文件（`*.map`、`package-lock.json`、`*.png`）。

> 为什么必须写死：本工作区实测噪声规模 —— `node_modules/` 3,415 文件、`gods-eye-view/`（第三方参考）536 文件、`tasks/` 11,126 文件。不预设排除名单，候选池会被噪声淹没，`fit_score` 随之失真。这不是理论风险，是可复算的事实。

### 3.2 三原语在检索快判中的对应

| Jev 原语 | 语义 | 本模块中的角色 |
| --- | --- | --- |
| **Choice** | 从 N 个里选 | ① 源类 `source_class`（五类，可组合）② 该类下的候选检索目标 `candidates[].source` |
| **Score** | 连续位置 + 置信 | `candidates[].fit_score`（每个候选对本步信息缺口的契合分 0–1）；R1–R5 维度分 |
| **Noul** | P(true) 是非判断 | `needs_retrieval`（本步到底要不要检索）；R5 的候选池纯净度判断 |

> ⚠️ **Noul 语义陷阱**：`P(true)` 本身就是信念强度，**不要把它当"置信度字段"再套一层阈值**；Score 的等级顺序写反是另一处高频坑。

## 4. 输入输出契约（Contract）

**输入（最小化；判定阶段不取额外上下文、不触发真检索）**：

```yaml
step_need:    str          # 本步需要什么信息（缺口描述）
step_clues:   str|null     # 已有线索 / 已排除项（可为空）
workspace:    str          # 工作区根 —— 决定"本机可得性"(R2) 的判定面
```

**输出（机器可读，逐条追加到 `plan.yaml` 的 `meta.检索判定` 列表，与 `meta.方法选用` 同构——每次检索一条）**：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `source_class` | `本地资产`\|`历史留痕`\|`知识库`\|`技能手册`\|`联网`（可 `+` 组合） | ✔ | Choice 源类。**枚举唯一取值源见 §1 表** |
| `candidates` | `[{source, fit_score}]` | ✔ | Choice(2..k) + Score：每个候选检索目标及其契合分（0–1） |
| `needs_retrieval` | bool | ✔ | Noul：本步到底需不需要检索（false → 直接做，不写决策记录） |
| `confidence` | float 0–1 | ✔ | = max(fit_score) 或主类置信 |
| `route_hint` | str | ✔ | 处理指引（见 §5），非空 |

**字段化而非散文**，是为了对齐 ai-workflow 既有的"机器可校验"风格（`入口判定`/`方法选用`/`模型档位`/`自研工具` 等同构）：判定结果可进账本、可回溯、可未来加判据。

## 5. 阈值路由（Threshold Routing）

| 区间 | 行为 |
| --- | --- |
| `needs_retrieval=false` 且 `confidence ≥ 0.95` | **不检索、直接做**；**允许**下否定断言（限"既有上下文已完整覆盖"时） |
| `needs_retrieval=true` 且 `confidence ≥ 0.95` | **自动检索** top candidate（fit_score 最高者） |
| `0.70 ≤ confidence < 0.95` | **中置信**：检索后**实读结果再采信**；**不得**仅凭 fit_score 断言；标记待复核 |
| `confidence < 0.70` **或** 候选间 fit_score 差距极小（歧义） | **fail-closed**：问一句"你要的是 X 还是 Y"，或**只报「未检索」** |

### 5.1 否定断言的证据门槛（**本模块的核心产出**）

> 这一节是本模块存在的主要理由：它把 SOUL.md 的准则「**「绿」有三种，必须分开报：通过 / 未检测 / 无法判定**——把后两种报成第一种，比漏判更危险」从**个人准则**变成**可留痕的判定**。

| 情形 | 允许的表述 | 禁止的表述 |
| --- | --- | --- |
| 已按本契约检索，且**出示了命中 0 的原始输出** | 「已检索 <源类清单>，0 命中」→ **可断言不存在** | — |
| 未检索，或只做了部分检索 | 「**未检索**，无法判定」 | ~~「不存在」「没有」「未使用」~~ |
| 检索了但**源类未覆盖全部五类** | 「在 A/B 内 0 命中；C/D/E **未检索**」→ **必须分报覆盖与未覆盖** | ~~笼统的「查过了，没有」~~ |

**判定规则（可留痕、可复核）**：

1. **否定断言必须附检索范围**：断言"不存在"时，`route_hint` 须写明**实际检索了哪几类源**，且该描述与 `candidates` 一致。
2. **未覆盖的源类必须显式列出**：五类中未检索的部分不得省略。
3. **"未检索"是一个合法且必须存在的结论**：它比一句自信的"没有"更有价值 —— 前者让人知道还缺什么，后者让人以为已经查过。

> ⚠️ **与 method-judge 低置信档的差别**：method-judge 低置信时"退回最保守手段"即可（手段是自选的）；本模块低置信时**不能**用"换个源再猜一次"来掩盖，因为**信息缺口不会因为换个源就消失** —— 只能如实报"未检索"。这是信息轴特有的不对称性。

**`route_hint` 按结论给出处理指引（规范后续检索的核心产出）**：

| 结论 | route_hint | 动作 |
| --- | --- | --- |
| 不检索 | 直接做 | 用既有上下文作答；若为否定断言，须注明依据来源 |
| 自动检索 | 检索 `<source>` | 查 top candidate；出示原始输出；写一条决策记录 |
| 中置信 | 检索 `<source>`（待复核） | 查 top 但**实读结果**再采信，标记待复核 |
| 模糊 / 歧义 | 澄清 | fail-closed：问一句，不猜；或只报"未检索" |

> ⚠️ **校准优先于准确率**：一个 67% 准确率但**完美校准**的判定器，比 90% 准确率却**错标**的更有路由价值——路由靠"概率可信"。这正是阈值取保守值（自动采信 0.95）的**理由**。
> ⚠️ **校准未经独立证实前，阈值取保守值**（自动采信 0.95、中置信一律走实读复核）——"自信地断言不存在"比"说不知道"危险得多。

## 6. 集成位置与机制

retrieval-judge 嵌入阶段 3 执行期，**落点 = 第 5 条（精确检索）之前、第 4 条（进度汇报）之后**：

```
阶段 3 每步：
  ① 重述目标与判定标准
  ② method-judge（该用什么手段）
  └─► [retrieval-judge 触发] → {source_class, candidates, needs_retrieval, confidence, route_hint}
        └─► 写入 plan.yaml 的 meta.检索判定（needs_retrieval=true 时才追加决策记录）
              └─► 驱动：
                    (a) 源类选择（本地资产/历史留痕/知识库/技能手册/联网）
                    (b) 具体检索目标（candidates 里 fit_score 最高者）
                    (c) 检索深度 + **能否下否定断言**（§5.1）
```

### 6.1 与各组件的协作方式

| 协作对象 | 关系 | 协作方式 |
| --- | --- | --- |
| **阶段 3 第 5 条「精确检索」** | **判据源 + 正交并存** | 它给工具清单（哪个源用什么工具）；本模块给"查哪类、查多深、能否断言"（见 §1.1） |
| **阶段 1 第 1 条「三类并行收集」** | 上游同源 | 那三类的词汇与本模块五类的映射：相关文件→本地资产；历史任务→历史留痕；交付物与台账→历史留痕 |
| **method-judge** | **正交并存** | 它判手段（含"事实类→联网"）；本模块判信息缺口与覆盖度。二者同构、不互相覆盖（见 §1.1） |
| **KB-First（阶段 0）** | 上游 | KB 已覆盖则本模块常判 `needs_retrieval=false`（`source_class=知识库` 已满足） |
| **`plan.yaml` / `checks.py plan`** | 留痕载体 | 判定落 `meta.检索判定`；检查项 16 校验（缺失 → WARN，见 §10） |
| **`meta.决策记录`** | 决策留痕 | `needs_retrieval=true` 时追加一条 `{决策点, 能力类, 依据, 选择, 时间}`（用 `checks.py decide`） |
| **SOUL.md「绿有三种」** | **判据来源** | §5.1 的否定断言门槛即该准则的工程化落地 |
| **独立审核 / 返修复查 / 熔断 / 反思重试** | **不参与** | 判别层不进入执行期闭环，不与 T1–T3、R1–R6 混用 |
| **红线③ / 出站扫描 / 口径守卫** | **不替代** | 安全关键门禁仍由确定性代码兜底，见 §8 |

## 7. 判定模型：双 Realization（由谁/什么执行判断）

### 7.1 结论：基础设计**不需要**独立训练的神经网络

retrieval-judge 的目的是"规范模型每次检索前的思考顺序"，由**主代理 LLM 自身**在动手前强制执行一次结构化快判即可达成——直接长在"大脑"里，**无需额外权重**。这是默认 realization。

但**必须显式定义"判定模型"**，否则"单次前向、无思维链"只是口号、落不到执行主体。故采用**双 realization**（与 self-judge §7 / method-judge §7 同构）：

| 维度 | **A 脑内协议**（默认，**本版启用**） | **B 独立 System 1 模型**（升级，**本版不启用**） |
| --- | --- | --- |
| 是否新增权重 | 否 | 是 |
| 与"大脑"耦合 | 同源，最贴"集成到大脑" | 解耦，作为外部快判节点 |
| 校准概率 | 间接（纪律 + few-shot 诱导） | 直接（RLCD 式校准目标） |
| 并行 fan-out | 不支持 | 支持（一次前向打包多个检索门） |
| 适用规模 | 单步、低频 | 高频、批量、需解耦 |

### 7.2 Realization A —— 脑内协议（默认，零新增依赖）

- **不是新模型**，而是主代理 LLM 的**自我约束协议**：把 §3 的四步判据写进阶段 3 第 5 条之前，强制其产出 §4 的结构化判定。
- **"模型"即推理纪律**：判定能力来自 LLM 既有的意图理解与上下文感知，由 schema + §9 判例锚 + §5.1 否定断言门槛 + fail-closed 兜底诱导出稳定输出；**无单独训练、无单独权重**。
- **诱导目标**：让判定分布尽量"校准"——手段 ① 固定 5 维 schema（防临场发挥）② §9 判例锚定边界 ③ 低置信强制"只报未检索"。
- **代价（诚实登记）**：未与执行解耦 → 判定不独立校准、不可并行多问、占用主模型一次前向。

### 7.3 Realization B —— 独立 System 1 决策模型（升级路径，**本版不启用**）

- **何时启用**：① 高频批量检索路由 ② 判定与主模型解耦以降成本 ③ 真正并行的 speculative fan-out（一次前向打包"该查哪类源?+能否断言?+覆盖够不够?"）④ 独立校准概率驱动阈值路由。
- **本地落地**：官方 Jev API **未向中国大陆开放**，不直连；若启用 B 走社区复现（OpenJev 冻结 Qwen3.5-4B + 受限 softmax）。
- **接口**：与 §4 **完全一致**，故 A ↔ B 切换对下游透明。

> **落地顺序（沿用前两个 judge 的用户既定约束）**：**只上 A**，不启用 B。契约不变，未来启用 B 不改下游。
>
> **时点注记（2026-09-23，v4.6.1）**：上述 **2026-09-22 的用户约束保持不变**（**只上 A**）。本机另已把 Realization B 的**本地落地实测打通** —— Laya `0.3.6` 离线 CPU 服务 + `scripts/laya_client.py`；但它当前**只作影子期对照后端**：**不参与路由、不接管判定、不进入执行期闭环**，retrieval-judge 的主判据仍是 Realization A。⚠️ 影子期后端**不得用于否定断言**（§5.1 的证据门槛不因它而放宽）；温度拟合前 `source_class` 与 `needs_retrieval` 阈值均不可采信。详见 `references/laya-backend.md`。

## 8. 不可委派与护栏

- **不授权写操作**：只输出"信息该从哪来"，**不输出"我可以做"**。工作区边界红线、写操作确认仍归确定性规则与人工。
- **不替代安全关键门禁**：红线③越界判定（`_check_scope`）、出站扫描（`scripts/outbound_scan.py`）、口径守卫（`_check_parity`）保留 AST/代码实现，retrieval-judge 仅作辅助信号。
- **不触发真检索**：判定阶段只读"本步需要什么信息"，**不发起实际检索**——否则"先判后查"的次序被打破，且退化成 System 2。
- **不越界**：判定只读本步的「需要什么信息 / 已有线索 / 工作区根」，不读全库。
- **不进入执行期闭环**：不参与独立审核、返修复查、熔断判定、反思重试。
- **理由**：概率校准尚未独立证实、且**可在 schema 内高置信判错**；"我查过了"这类断言不能押在 unverified 模型上。

## 9. 判定样例锚（边界判例，供 Realization A 的 few-shot 锚定）

> 作用：把"该查哪类源、查多深"的边界锚成**可复用判例**，而不是每次临场发挥。列 5 条种子判例，首次使用后可继续追加。

| # | 本步需要什么信息 | source_class | candidates（fit_score） | needs_retrieval | 备注 |
| --- | --- | --- | --- | --- | --- |
| 1 | "这个库有哪些可复用的 PPT 主题" | 本地资产 | `src/deck/themes/`(0.95) / `README.md`(0.60) | true | 高置信→直接扫目录；先过 §3.1 排除名单 |
| 2 | "上一轮性能优化实测了多少 draw call" | 历史留痕 | `tasks/性能优化-2026-09-11/`(0.95) / `Ledger.md`(0.70) | true | 留痕可复用，不必重测（效率项：检索结果复用） |
| 3 | "React 19.3 与 R3F 9.7 是否兼容" | 联网 | GitHub API(0.90) / 网页检索(0.60) | true | 当世事实，本机推不出 |
| 4 | "把这个函数改成纯函数" | — | — | **false** | 纯推理，信息已在上下文，不写记录 |
| 5 | "库里有没有饼图组件" | 本地资产 | `src/three/Chart3D/`(0.95) | true | **否定断言场景**：查完才可说"没有"；**未查只能说"未检索"** |

**判例 5 是重点**：它不是"判不出来所以要猜"，而是"**这类结论必须先有检索范围才允许出口**"。用户问"有没有 X"时，最差回答不是"有"或"没有"，而是**没查就说的"没有"**——那会让用户以为已经找过了。

## 10. 诚实边界与验收

沿用本技能一贯的"诚实边界"风格：**写在提示里的门禁不是门禁**。

1. ⚠️ **校准不可机器强制** —— `confidence` 由模型自填，**无法被工具证明"真的校准"**。它是**纪律 + 留痕项，不是门禁**。任何"已由工具保证校准"的说法都不成立。
2. ⚠️ **缺失 `meta.检索判定` 不是 FAIL，是 WARN** —— `checks.py plan` 检查项 16 的口径：整段缺省 → **WARN**（向后兼容旧 plan，**不追认历史计划**）；一旦填写，结构非法 → **FAIL**（沿用"可选字段、填了就不能糊弄"）。**不得宣称该字段是强制门禁。**
3. ⚠️ **「未检索」与「不存在」的区分无法被机器强制** —— 这是本模块**最重要的诚实边界**。机器能校验 `needs_retrieval` 是 bool、`candidates` 结构合法，**不能校验**"你写的那句『没有』背后是否真查过"。§5.1 是**纪律 + 留痕**，不是门禁。任何"已由工具保证不会误报不存在"的说法都不成立。
4. ⚠️ **判定也会判错** —— 下游必须可观测、可复核；判定结果随步骤留痕（`meta.检索判定`），便于回检"当时为什么判为本地资产类"。
5. ⚠️ **类型合法 ≠ 判断正确** —— 本模块保证输出**落在五类之内**（零类型错误），**不保证源类选对、不保证查全**。"结构合规"≠"覆盖充分"。
6. ⚠️ **判错比不判更危险** —— 故低置信一律降级到"澄清 / 只报未检索"（fail-closed），自动采信阈值取保守值 0.95。

**验收信号（可判定）**：

| 信号 | 判定方式 |
| --- | --- |
| 含检索的步骤，其 `plan.yaml` 含 `meta.检索判定` 且 `source_class` ∈ 五类（+组合） | 机器（`checks.py plan` 检查项 16） |
| `needs_retrieval=false` 的步骤确实没写决策记录 | 人审（查 `meta.决策记录` 是否多余） |
| 否定断言的**检索范围**与 `candidates` 一致、未覆盖源类已显式列出 | **人审** —— 机器只能校验字段结构，**不能校验表述与事实是否相符**（见 §10.3） |
| 抽样历史步骤，源类选择与人工复核**一致率** | **人审** —— `checks.py plan` **检查项 17** 只做**机器指路**：把**抽样池**（`needs_retrieval=true` 或 `confidence < 0.95` 的条目）列出来出 WARN，**判定仍靠人**。未证实前只报"**一致率**"，**不声称"准确率"** |

> ⚠️ **检查项 17 是"指路"不是"门禁"**：它把"该抽样看哪里"标出来，**不判定"查得够不够"**（机器做不到），故**永不计入 FAIL、不改退出码**。
