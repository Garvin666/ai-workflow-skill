# 子代理并行编排手册（阶段 3 按需加载）

## 一、Handoff 结构化交接（必填字段，禁止自由文本）

派发子代理时，提示必须包含以下字段。缺字段 = 交接失败，主代理需重写：

```
task:              一句话说明做什么（动词开头，单一职责）
background:        项目背景、划界说明（不覆盖什么）、目标读者
input_paths:       输入文件的绝对路径（无输入则写"纯联网调研"）
acceptance:        可验收标准，逐条可判定（如"≥2 个来源各标 URL"）
deliverable_path:  产出落盘绝对路径（含文件名）
evidence_rule:     证据标注要求（如"每条要点标来源 URL，区分实测与观点"）
```

**反例**：「帮我调研一下 RAG 框架」——无验收、无路径、无划界，产出必然不可用。
**正例**：见本日实际派发（四个方向各含上述字段 + "不要重复今日已有调研的 XX 话题"）。

## 二、并行 / 串行判定

| 情形 | 决策 |
| --- | --- |
| 子任务之间无数据依赖（如四个方向的检索） | **并行**派发，单条消息内多个调用 |
| B 需要 A 的产出（如先查重再实现） | **串行**，禁止并行 |
| 需要主代理结果才能决定下一步 | 前台等待（非 background） |
| 与主线无关的长任务 | background + 完成后通知 |

**并行上限**：建议 ≤4 个。理由：① 审查端会先饱和（DORA：作者侧提速转化为审查者侧认知负荷）② 匿名 API/配额类接口易被并发打满（今日 GitHub 403 即为此）。

## 三、子代理类型与模型选择

| 用途 | 子代理类型 | 模型档位 |
| --- | --- | --- |
| 探索/找文件/读日志（高噪音只读） | Explore | 轻量（lite） |
| 方案设计/架构评估 | Plan | 默认/推理 |
| 写码执行、生成类 | general-purpose | 默认 |
| 批量检索/分方向调研 | general-purpose | 轻量（省 token） |

原则：**能标注"只读研究"的绝不给写权限**；只读研究类用便宜模型（成本可差 15×）。

## 四、产出回收纪律

- 子代理**只回传浓缩结论**（1-2k token）+ 关键数据表；长内容落盘，主代理按需读片段。
- 主代理**不得预读**子代理全部中间产物（违背 Token 纪律）。
- 回收后立刻做「信任但验证」：抽查可复现的硬数据（API 实测值、文件存在性、关键数字），至少 1 条交叉验证。

## 五、失败与升级路径

1. 产出不合格 → 带**具体问题清单**退回重做（最多 2 轮）。
2. 2 轮仍不合格 → 停止单线返工，改派**两个子代理独立审查该产出并互相质证**，主代理汇总裁决。
3. 仍不合格 → 升级用户，说明已尝试的路径与卡点，不静默降级交付。
4. 子代理报告的数据与主代理复核不一致 → **以可复现的一方为准**，并在交付说明中标注差异（今日实例：子代理实测 OpenHands 87,134 star 与主代理复核完全一致，方法可信；其余因限流未复核，已在交付说明中标注）。

## 六、编排反模式速查

- 子任务描述含糊（"帮忙改代码"永远路由不对）→ 写清触发条件与交付物。
- 只读研究型子代理给了 write/bash → 隔离保证失效。
- 把有依赖的任务并行化 → 结果错乱且难以归因。
- 用子代理干琐事（格式化 JSON、跑一条命令）→ 开销大于收益。
- 把子代理当"外包"而非"受控协作"→ 必须结构化交接 + 回收验证。
