# 质量门禁与证据纪律（阶段 2/3/5 按需加载）

> 依据：《调研-AI工作效率与质量提升-2026-09-10》+《调研-模型路由与工作流编排-2026-09-10》

## 一、证据分级标注（阶段 2 强制）

每条关键结论必须标注证据强度，未标注的视为【实践观点】：

| 标记 | 含义 | 可否作为决策依据 |
| --- | --- | --- |
| 【RCT】 | 随机对照试验实测行为数据 | 可，但需核对适用边界 |
| 【基准实测】 | 受控基准上可复现的数据 | 可 |
| 【大样本自评】 | 数千人问卷，测的是**感知** | 仅作参考，不得当业绩数据 |
| 【官方推荐】 | 厂商/项目官方最佳实践 | 可作方法依据，**非效果证据** |
| 【实践观点】 | 一线开发者个案经验（n=1 居多） | 仅作线索 |
| 【反例】 | 与主流叙事相悖的证据 | 必须并陈，不得隐去 |

**硬禁令**：厂商案例（如"52 周压缩到 3 周"）、营销倍数（"3-5× 效率"）、二手转述的 star 数/基准分数，一律不得作为证据引用。

## 二、验证闭环（阶段 3 前置硬门禁）

动手前必须回答：**这个任务完成时，用什么可判定的信号证明它成了？**

| 任务类型 | 可判定信号 |
| --- | --- |
| 写代码/改代码 | 测试套件、构建退出码、linter、类型检查 |
| 数据分析 | 交叉校验脚本（总额对账、行数一致、空值率）、抽样复算 |
| 报告/文档 | 验收标准逐条对照表、来源可溯（每条结论有 URL/文件） |
| 爬取/数据抓取 | 抓取条数、字段完整性断言、重复率检查 |
| 自动化/编排 | dry-run 输出、幂等性复跑一致 |

无信号 → **先补最小验证物再开工**；补不了 → 在 plan.yaml 显式登记「人审点」，交付时明说未验证部分。

**交付原则：出示证据而非声称成功**——贴测试输出、命令返回值、文件清单，不接受"应该没问题"。

## 三、CI 门禁（编码类任务）

| 门禁 | 免费工具 | 建议阈值 | 为什么需要 |
| --- | --- | --- | --- |
| **变异分**（替代覆盖率） | mutmut（Py）/ Stryker（JS） | 变更文件 ≥60% | AI 常生成"调用了但不断言"的测试，覆盖率会骗人 |
| 圈复杂度 | lizard / radon | 单函数 ≤15 | AI 爱写超长深嵌套函数 |
| 契约不静默变更 | oasdiff / 契约测试 | breaking 即 fail | AI 会顺手改响应结构 |
| 依赖审计 | pip-audit / npm audit | 高危即阻断 | AI 会引入可疑/废弃包 |
| 密钥扫描 | gitleaks / trufflehog | 0 容忍 | 示例代码常含"像真的"凭据 |
| SAST | semgrep / CodeQL / SonarQube | 高危即阻断 | **至少叠加 2 款**（单工具对 AI 代码识别率 <22%） |

**红线**：资金/权限/认证/加密相关代码禁止纯 AI 生成，必须人工逐行复核；**实现与测试不得由同一模型包办**（自我确认错误）。

## 四、LLM 评审六偏差与去偏（评审由模型完成时必须防）

| 偏差 | 表现 | 去偏手段 |
| --- | --- | --- |
| 位置偏差 | 交换 A/B 顺序裁决翻转 | A→B 与 B→A 各跑一次，两次一致才算赢 |
| 冗长偏差 | >90% 情况选更长答案 | rubric 写明"长度本身不加分，信噪比才加分" |
| 自我偏好 | 给自己/同家族输出打高分（10-25%） | 裁判与被评模型**异家族** |
| **风格偏差** | 偏好 markdown/加粗/列表，量级 0.10-0.76（**最被忽视**） | 格式归一化；rubric 声明格式不计分 |
| 指令泄漏 | rubric 暴露导致"刷分" | 盲评或分步评分 |
| 校准差/复现性 | 置信度高于实际准确率；版本更新致判决漂移 | pin 裁判版本；容差带代替精确阈值 |

**省钱要点**：中端模型 + 正确去偏可超过顶级裁判，成本约低 15×（arXiv 2604.23178）——本地 Ollama 模型当裁判完全可行，但须先用人审样本做"裁判体检"（一致性/翻转率）。

## 五、反模式清单（持续追加）

### 编排类
1. 把有依赖关系的任务并行化（B 需 A 的产出必须串行）。
2. 用子代理干琐事（格式化 JSON、跑一条命令）。
3. 子代理只读研究却给了写权限——隔离保证失效。
4. 主上下文预读全部子代理的长输出（应只收 1-2k token 浓缩结论）。
5. 并行的真瓶颈在审查端：审查饱和就停下，别继续加压。

### 上下文类
6. 提交 `/init` 自动生成的上下文文件（实测 -3% 成功率、+20% 成本）。
7. 上下文文件写"仓库架构概览/目录说明"等模型能自己推断的内容。
8. 把上下文压到 90%+ 求"省成本"（会重新取数，总成本反升）。
9. 长人设堆砌（约束与上下文比 persona 更有效）。

### 度量与决策类
10. 用自己的感觉度量效率（实测与自感知可差 39 个百分点）。
11. 把"生成速率"当"交付速率"（瓶颈会迁移到审查/集成）。
12. 引用二手 star 数或营销倍数当决策依据。
13. 用覆盖率当质量门禁（应看变异分）。
14. 一次性信任 LLM 裁判（偏差随模型版本漂移，须定期重新审计）。

### 流程类
15. 同一问题纠正超过 2 次仍继续打补丁（应重开会话 + 换更好的初始提示）。
16. 规格/计划与代码脱同步后继续执行（Agent 会自信地按过时规格执行且不报警）。
17. 未做完 Anti-drop 对账就交付（静默跳过步骤）。
18. **计划标了"完成"就当"已交付"**——对账要落到文件系统（路径存在），实战中正是它抓出「step 4 标完成但 xlsx 不存在」。
19. **自检/对账工具在依赖或输入缺失时仍输出"全绿"**（如缺 pyyaml 却打印 `FAIL=0` 且退出码 0）——工具本身必须先满足"未跑起来就不能报通过"，否则所有下游判断都是假的。
20. **外链未探活就写进交付物**——子代理转述的 URL 极易错（实战抓到 OWASP ZAP 死链）；交付前用 `http_fetch --check-links` 并发探活，403 属反爬不属失效需区分标注。
21. **把某次实测的加速/耗时当成普适结论**（如"40× 加速"只对"只探活不下载"这一场景成立）。
22. **采信子代理的"看起来合理"的链接**——实战抓到编造的日期型 URL（`/2026/04/17/...`，站点根 200 而该路径 404，原文自带省略号），且它正被用来支撑一条结论。**日期型/带省略号的 URL 一律先探活再采信。**
23. **把本机环境限制误判为信息失效**——本机出口隧道对 `huggingface.co`/`jina.ai`/`console.cloud.google.com` 稳定返回 502，应标注"本机无法验证"，不得写成"该站点已下线"。
24. **把"接口能用"当成"配额够用"**——GitHub 匿名 core 仅 60 次/小时，一次 35 仓库的批量实测就会打满并被迫分批等待。设计批量取数前先查配额与重置时间。
25. **用 star 数代替活跃度**——实战中 `ugrep` 本体 3,284★ 且近期有提交，看起来健康，但其**索引器组件只有 84★ 且停更 14 个月**。star 高的仓库，子组件可能是死的：必须**逐组件**核实 `pushed_at`。
26. **只看 `license` 字段就判定可用性**——`codeql` 仓库元数据标 MIT（仅覆盖查询与文档，CLI 引擎另有专有许可）；`NOASSERTION` 是"无法自动判定"而非"无许可证"。选型必须人工打开 LICENSE 核实。
27. **在 YAML 未加引号的值里写 ASCII 冒号**（如 `（A: xxx）`）→ `mapping values are not allowed here`，plan.yaml 直接废掉。用全角冒号或加引号。
28. **只测耗时、不做输出比对就宣称"性能优化完成"**——耗时降了不等于统计没改坏。性能改动的验收信号必须是**双条件**：耗时下降 **且** 输出与旧版**逐字节一致**（v2.4.2 实战：`--top` 传错一个参数就出现"前 12/前 15"差异，靠比对当场发现"没改坏"这个结论站不住）。
29. **不控变量、不预热就报加速比**——冷缓存会凭空造出"加速"。正确做法：**预热后再计时、同一目录同一参数、多次取最小值**，并**独立复现 ≥2 轮**看结果是否落在同一区间（v2.4.2 实测 9.55× 与 10.04× 两轮互相印证，取保守值）。尤其要提防**基线是冷的、优化后是热的**这种"假加速"。
30. **把端到端耗时当成被优化那一段的耗时**——`data_query.py files` 热机 4.0s 里只有约 2.3s 是遍历，其余是扩展名聚合+排序（1.4s）与解释器启动。**性能问题必须先把总耗时拆成几段分别计时**，否则会在错误的段落上做优化、或在正确的优化上误判"没效果"。
31. **凭据"看起来没有"就当没有，或把命令输出直接当凭据**——`gh auth status` 在部分上下文会误报未登录，而 `gh auth token` 实际有可用凭据；反向的坑更危险：该命令失败时输出的提示文本（如 `no oauth token found for github.com`，约 40 字符）会被当成 token 发出去。**凭据必须做形态校验**：前缀（`ghp_`/`gho_`/`github_pat_` 等）或 40 位十六进制、长度 ≥20、无空白，且要区分"退出码为 0"与"输出确实是凭据"。
32. **把「反爬拦截」当成「链接失效」**——403 至少分四类：CDN/WAF 反爬、限流、需授权、未知拒绝；只有 404 才等于失效。探活工具必须输出**分类**而非单一 403 状态，否则会把可人工访问的页面误判为死链而错改引用。本次同时厘清：`academy.hackthebox.com` 的真实失败是 **SSL 握手超时（本机出口限制）**，与反爬无关，两类问题不得混写。
33. **改造默认口径却不留旧口径开关**——"跳过依赖目录"这类默认行为变更，必须保留回退开关（`--no-skip`/`--legacy-skip`）并把**旧口径逐字节复现**当作验收证据（本次 488 行完全一致），否则历史报告与旧结论无法复核。
34. **把凭据打印进日志/会话**——验证 token 解析时随手 `print(token)` 会让真实凭据落进会话记录（本次实测即发生）。**凭据只能输出前缀掩码 + 长度**（如 `gho_***（40 字符）`），任何情况下不得打印完整值，也不得写入记忆或文件。
35. **读写越出本次任务的工作区根而未申请授权**——工作区根由用户按任务指定（确认表 `workspace` / plan.yaml `工作区根`）；根目录之外的任何路径都必须**先停下来说明再取得当次授权**。典型越界：图省事直接读上级目录、把产出写到根目录之外、拿上次任务的授权当本次授权。基础设施例外（skill 目录 / venv / 缓存目录）仅限工具用途，**不得用来存放用户数据或产出**。
36. **在模板/计划里省略工作区根字段**——`workspace` 与 `工作区根` 是**必填**，缺失时 `checks.py plan` 会直接 FAIL；开工前不填等于没有边界声明，后续任何越界都无从判定。
