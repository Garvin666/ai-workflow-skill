# 项目 Git 开发规范（写代码 / 改方案 / 生成 commit 时适用）

> 状态：v1（2026-09-22 建立，随 ai-workflow v4.6.0 发布）。
> **唯一事实源** —— 本文件是 ai-workflow 内「分支模型 / commit 注释规范 / 禁止提交清单 / 开发流程」的**唯一口径源**。
> **何时加载（勿预读）**：任务涉及 ① 编写或修改代码 ② 新建模块或实验分支 ③ 生成 commit 信息 ④ 配置 `.gitignore` ⑤ 合并分支 —— 阶段 3 执行期与阶段 5 交付前按需加载。
> **与 `push-routing.md` 的分界**：本文件管**本地仓库的分支与提交**；`push-routing.md` 管**推送到 public 仓的通道机制**（自研工具/技能分流、blob sha 一致性、独立验收）。同一件事不写两处（技能硬约定第 4 条），分界表见 §6。

---

## 一、适用范围与来源

**适用**：任何纳入 git 管理的代码项目 —— 量化系统（FastAPI + Qlib + React）、前端组件库、DAG 工作流引擎、Skill 本体、实验脚本。

**不适用**：不纳入 git 的一次性脚本、无代码仓的纯文档产出、只读调研任务。

> **来源与改写边界**：本规范由 Garvin 于 2026-09-22 给出 **5 条规则**（原话见 `tasks/技能增强-ai-workflow-v4.6.0-2026-09-22/确认表.md`）。**本文件不扩展、不改写这 5 条**。下文凡属「本规范补的工程默认值」（scope 可选、合并用 `--no-ff` 等）**逐处显式标注**，与用户原话区分 —— 不把补充当要求，也不把要求当建议。

## 二、分支模型

### 2.1 三条职责线

| 分支 | 职责 | 禁止 |
| --- | --- | --- |
| `main` | 存放**稳定可运行**版本 | **禁止直接在 main 开发新功能**（规则①） |
| `dev` | 新功能 / 实验调试 / 新增模块的**集成分支** | 禁止把未本地测试的代码合入 `main` |
| `exp-xxx` | **并行**实验的独立分支，从 `dev` 切出 | 禁止多个并行实验共用一个分支 |

> 用户原话（规则②）：**所有新功能、实验调试、新增模块（Jeff/Jev、DAG 工作流、Skill），全部在 dev 分支开发；多个并行实验，新建独立 exp-xxx 分支。**

### 2.2 命名规则

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 稳定线 | 固定 `main` | `main` |
| 开发线 | 固定 `dev` | `dev` |
| 实验线 | `exp-<主题>`，主题用小写英文短横线 | `exp-dag-scheduler`、`exp-jev-router`、`exp-skill-index` |

**禁止**：`test` / `tmp` / `new` / `1` 这类无信息名；中文分支名（跨平台与 CI 的编码风险）；`exp-` 后留空。

### 2.3 生命周期

```
exp-xxx ──验证通过──► dev ──稳定──► main
```

1. `exp-xxx` 结论被采纳 → 合回 `dev`（**不直接进 main**）。
2. `dev` 在完整测试通过后 → 合并到 `main`（规则⑤）。
3. `exp-xxx` 合并后**默认保留**到该实验结论被 `dev` 吸收后的下一个发布点 —— 分支是实验证据的一部分，早删会丢掉"当时怎么试的"。
4. 合并方式：默认 `git merge --no-ff`（**本规范补的默认值**，用户未指定）—— 保留合并记录便于回滚定位；用户偏好快进时改用 `--ff-only`。
5. **分支迁移是结构变更**：把既有 main-only 仓库改造成 `main` + `dev` 双线，属**对外可见且影响协作**的动作，须先按 SKILL.md 阶段 5 第 8 条出内容清单与回滚方式并取得确认 —— 本规范**不授权自动迁移**。

## 三、commit 注释规范

### 3.1 格式

```
<类型>: <描述>
```

- **类型必填**，取自 §3.2 的枚举；类型后为 ASCII 冒号 + 一个空格（`: `）。
- **描述**中英文均可，**动词开头、说清"做了什么"**；禁止 `update`、`修改一下`、`fix bug` 这类无信息描述。

**可选扩展（本规范补，用户未要求、亦未禁止）**：

| 扩展 | 写法 | 说明 |
| --- | --- | --- |
| 影响范围 scope | `feat(auth): 新增 JWT 刷新` | 括号内为受影响模块；可选 |
| 破坏性变更 | `refactor!: 移除旧接口` | 类型后加 `!`；可选，用于接口不兼容的改动 |

> scope 与 `!` 均为**可选**：不写即符合规范，写了同样符合。**唯一硬要求是「类型 + 冒号 + 描述」三件套。**

### 3.2 类型表（机器可读声明 —— 口径守卫锚点）

| 类型 | 含义 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | 修复 bug |
| `refactor` | 代码重构，功能不变 |
| `docs` | 更新文档注释 |

> ⚠️ **这张表是口径守卫锚点**：`scripts/checks_parity.py` 的 `_p_commit_types` 解析本表首列，断言其与 `scripts/checks_core.py` 的 `VALID_COMMIT_TYPES` 是**同一集合**。**改本表就必须同步改常量**，否则 `checks.py skill` 直接 FAIL。
> ⚠️ **不得自行扩展类型**。需要 `chore`（构建/依赖）、`perf`（性能）、`test`（测试）等时，须**先经用户确认**，再同步**三处**：本表 → `scripts/checks_core.py` 的 `VALID_COMMIT_TYPES` → `scripts/git_check.py` 的 `COMMIT_TYPES`。沿用技能既有口径：**不得自行编号，无匹配项时先扩规则再同步代码**。

### 3.3 描述写什么

| 场景 | 差 | 好 |
| --- | --- | --- |
| 新增 | `feat: 加了个接口` | `feat: 新增选品比价接口 /api/compare` |
| 修复 | `fix: 修好了` | `fix: 修正汇率换算漏乘含税系数导致的比价偏高` |
| 重构 | `refactor: 改了下` | `refactor: 抽出 VolumeCaliber 统一成交量口径，行为不变` |
| 文档 | `docs: 更新` | `docs: 补 v4.6.0 变更记录与 Git 规范索引` |

**判据**：把这条 commit 单独拿出来，能否回答"改了什么、为什么" —— 答不上就是无信息描述。

## 四、禁止提交清单与 `.gitignore`

### 4.1 五类禁止提交（用户规则④）

| 序 | 类别 | 典型文件 / 目录 | 为什么 |
| --- | --- | --- | --- |
| ① | **模型权重** | `*.pt` `*.pth` `*.ckpt` `*.safetensors` `*.bin` `*.onnx` `*.h5`；`models/` `weights/` `checkpoints/` | 单文件常达 GB 级，Git 历史不可回收 |
| ② | **数据集** | `data/` `datasets/` `raw/`；`*.parquet` `*.tfrecord` `*.jsonl`（大样本） | 体积大 + 常含隐私/商业数据 |
| ③ | **虚拟环境目录** | `.venv/` `venv/` `env/` `__pycache__/` `node_modules/` | 可重建，且含平台相关二进制 |
| ④ | **日志** | `*.log` `logs/` `*.out` | 运行期噪音，且易夹带路径/凭据 |
| ⑤ | **密钥** | `.env` `.env.*` `*.pem` `*.key` `secrets.*` `*.p12` | **凭据永不落盘（信息安全底线 S1）** |

> 用户原话：**禁止提交：模型权重、数据集、虚拟环境目录、日志、密钥 .env 文件，使用 .gitignore 过滤。**

**注**：`*.jsonl` 与 `*.csv` 属"看情况" —— 小体积、脱敏的配置或样例可以入库；判定标准是**体积 + 是否含隐私**，不是扩展名。拿不准时按"不入库"处理，并在 `.gitignore` 里显式写例外（`!data/sample.csv`）。

### 4.2 `.gitignore` 模板

直接复制 `assets/gitignore-template.txt` 到项目根；它按 §4.1 的**五类分节**组织，每节带注释说明归属哪一类。

### 4.3 已经误提交了怎么办

| 状态 | 处置 | 风险 |
| --- | --- | --- |
| **未推送** | `git rm --cached <path>` → 补 `.gitignore` → 重新提交（或 `--amend`） | 低；历史仅本地 |
| **已推送（非密钥）** | 按阶段 5 第 8 条出**内容清单 + 可见性 + 回滚方式**取得确认 → `git filter-repo` / BFG 重写历史 → 强推 | **高**：重写历史影响所有协作者；强推属不可逆动作 |
| **已推送且含密钥** | **不是熔断，是安全事件** —— 立即停对外动作，走 `secret-leak-response` 处置（见 SKILL.md 熔断机制节末条） | **删历史 ≠ 密钥失效**：必须**轮换密钥**，并判断是否需告知受影响方 |

> ⚠️ `git rm --cached` **只让文件退出跟踪，不删磁盘文件**（这正是想要的效果：本地还留着，仓库不再收）。若误用 `git rm`（不带 `--cached`）会连本地文件一起删 —— **先确认命令再执行**。

## 五、开发流程（五步，用户规则⑤）

```
① dev 分支编码  →  ② 本地测试  →  ③ commit 提交  →  ④ 推远程 dev  →  ⑤ 验证稳定后合并 main
```

| 步 | 动作 | 可机器验证的判定信号 |
| --- | --- | --- |
| ① | `git switch dev`（并行实验用 `git switch -c exp-xxx`） | `git branch --show-current` 的返回值**不是** `main` |
| ② | 跑测试 / 构建 / 冒烟 | 命令**退出码 0**，且贴出原始输出（不接受"应该没问题"） |
| ③ | 按 §3 写 commit 信息并提交 | `python scripts/git_check.py msg "<信息>"` → 退出码 0 |
| ④ | `git push origin dev`（实验分支推 `origin exp-xxx`） | 推送成功 + 远端分支可见 |
| ⑤ | 在 `dev` 上确认稳定后 `git switch main && git merge --no-ff dev` | `main` 上测试全绿 + 人工确认；合并后 `main` 可直接运行 |

> ⚠️ **第 ④⑤ 步不是"顺手做"的动作**：推远端与合并到 `main` 都改变他人可见的状态，按 SKILL.md 阶段 5 第 8 条**先出内容清单 + 可见性 + 回滚方式**再执行，执行后登记 `meta.不可逆副作用`。
> ⚠️ **禁止跳步**：在 `main` 上直接编码 = 违反规则①；未本地测试就推 `dev` = 让集成线失去意义。

## 六、与 `push-routing.md` 的分界

| 维度 | 本文件（git-conventions） | `push-routing.md` |
| --- | --- | --- |
| 管什么 | **本地仓**的分支与提交 | **推送 public 仓**的通道机制 |
| 关键问题 | 改在哪个分支、commit 怎么写、什么不能提交 | 自研工具/技能怎么分流两仓、blob sha 是否一致、谁做独立验收 |
| 触发时机 | 阶段 3 编码期 + 阶段 5 交付前 | 阶段 6 沉淀期 |
| 共同点 | 都要求**推送前先取得确认**（不可逆动作） | 同左 |

> 一句话：**本文件说"提交到哪个分支"，`push-routing.md` 说"怎么把文件推上 public 仓"。** 两者不重叠，也不互相替代 —— 走 `push_router.py` 推 public 仓之前，本文件的 §4（禁提交清单）仍然生效。

## 七、机器校验（`scripts/git_check.py`）

```bash
# ① 校验 commit 注释是否合规（提交前跑）
python scripts/git_check.py msg "feat: 新增 DAG 工作流调度器"

# ② 校验项目 .gitignore 是否覆盖五类禁止提交
python scripts/git_check.py ignore <项目目录>

# ③ 校验当前分支状态（是否在 main 上直接改代码）
python scripts/git_check.py branch [--repo <仓库目录>]

# ④ 综合预检（branch + ignore，任务开工前跑一次）
python scripts/git_check.py preflight --repo <仓库目录>
```

**退出码**：`0` 全部通过 ／ `1` 有 FAIL（不合规） ／ `2` 用法错误。

**何时跑**：① 每次生成 commit 信息前（`msg`）；② 新项目首次配置或改动 `.gitignore` 后（`ignore`）；③ 开工写代码前（`preflight`）。

## 八、诚实边界（如实登记，不假装有保护）

- **`.gitignore` 覆盖率检查是启发式** —— 按模式关键词匹配。若项目用了非标准路径名（如 `my-weights/`）或自定义写法，可能**误报"未覆盖"**。脚本会列出该类的推荐模式供人判断，**不声称"没报就是覆盖全了"**。
- **`branch` 检查判不出"是不是新功能"** —— 机器只能发现"`main` 上存在未提交改动"，无法区分那是新功能开发还是文档修正，故只出 **WARN**，由人判断。
- **commit 描述的"质量"不可机器判定** —— 只有「类型 + 冒号 + 描述」的**格式**可判；`fix: 修好了` 能通过格式校验却是坏描述（§3.3 是纪律 + 人审，不是门禁）。
- **本规范不自动执行任何 git 写操作** —— `git_check.py` 是**只读校验器**，不切分支、不提交、不推送。所有变更动作仍由执行者按红线①（用户确认前不执行）发起。
- **口径守卫只覆盖"提交类型"这一个物理量** —— 分支名规则、禁提交清单均**未被机器守卫**，只写在本文件里；它们靠执行者遵守 + 阶段 5 自检。
