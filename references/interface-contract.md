# 自研工具接口契约（v4.44.0 起）

> **定位**：`scripts/` 下自研脚本的**对外调用面**（命令行参数、退出码、输出形态）的单一事实源。
> 契约由 `scripts/iface_lint.py` 机器校验；本文定义语义，工具执行校验，两处不得各写一套。
>
> **适用面**：所有带 `if __name__ == "__main__"` 的可执行脚本。纯内部模块（`checks_core.py`、
> `checks_parity.py`、`checks_judges.py`、`checks_cmds.py`、`_probe_argv.py`）不在射程内。

## 一、退出码契约

四个值，按「结论是否可得」划分，而不是按「严重程度」划分。这条分界与本仓的核心纪律同构：
**未检测不等于通过** —— 所以「无法判定」必须有自己的码，不能借用 1 或 0。

| 码 | 含义 | 典型情形 |
| --- | --- | --- |
| **0** | 成功，且结论为「通过」 | 检查全绿；命令正常完成 |
| **1** | **得出的结论是「不通过」** | 存在 FAIL 项；校验器判定不合规 |
| **2** | 用法错误或前置条件不满足 | 参数非法、必填项缺失、目标路径不存在、依赖未安装 |
| **3** | **无法判定**（既不是通过，也不是不通过） | 检查器全部不可用只剩 SKIP；外部服务不可达；`gate.py` 的 fail-closed 拒绝执行 |

**为什么 3 必须独立**：`check_vector_export.py` 在「所有后端都不可用、结果全是 SKIP」时返回 3，
`diagram_export.py` 在 PNG 通道全失败时返回 3，`laya_client.py` 在服务不可达时返回 3，
`gate.py` 在无法判定访问范围时返回 3。四处实现各自独立写出，语义却一致：
**说「过」没证据，说「不过」也没证据**。若把它们并进 1，调用方会把「没测成」读成「测出问题」；
并进 0 更糟，会把「没测成」读成「没问题」。

**判据（`iface_lint --check` 的 C2）**：脚本 `main` 路径上出现的退出码必须 ⊆ {0,1,2,3}。
**射程说明**：只统计 `main()` 函数体与 `__main__` 块里的 `return N` / `sys.exit(N)`。
函数内部的 `return 15`（HTTP 退避秒数）、`return 8731`（服务端口）不算退出码 ——
首版扫描器正是把它们误认成退出码，这条射程说明是踩过之后补的。

## 二、参数契约

### 2.1 不做名义统一（这是一条刻意的决定）

开工时实测到根路径类参数有三套名字：`--base` 9 个脚本、`--root` 6 个、`--workspace` 3 个。
看起来像命名混乱，逐个核对语义后发现它们**确实在说三件不同的事**：

| 参数 | 语义 | 例子 |
| --- | --- | --- |
| `--base` | **相对路径的解析基准** | `checks.py plan --base <工作区根>`：plan 里写的相对路径按它解析 |
| `--root` | **被操作对象的根** | `memory_handoff.py --root <40-记忆>`：落位与统计的范围 |
| `--workspace` | **额外纳入的工作区** | `gen_skill_index.py --workspace <目录>`：主扫描根之外的补充 |

把三者统一成 `--base` 会造出一个**错的抽象**：`memory_handoff.py --root` 指的是记忆库本身，
不是"解析基准"；改名之后调用方会以为它和 `checks.py --base` 同义，而它们不同义。
强行统一还会破坏既有调用面（`SKILL.md` 命令块、`ops.md`、历史任务脚本）。

所以契约取**登记制**，不取改名制：

- 每个根路径类参数（`--base` / `--root` / `--workspace`，以及将来新增的任何同类参数）
  **必须在 §2.2 语义表里登记**，写明它属于哪一类语义。
- 未登记的新参数名 → C3 判 FAIL。新增语义必须先想清楚"它到底是不是解析基准"，再落表。

### 2.2 根路径参数语义表

| 参数 | 语义类别 | 首次登记 | 使用脚本 |
| --- | --- | --- | --- |
| `--base` | 相对路径解析基准 | v4.44.0 | `checks.py` `gate.py` `cleanup_task.py` `push_router.py` `push_ontology.py` `laya_client.py` `laya_ensure.py` `laya_record.py` |
| `--root` | 被操作对象的根目录 | v4.44.0 | `archive_tasks.py` `external_skill_lint.py` `guard_constants.py` `memory_handoff.py` `push_router.py` `push_ontology.py` |
| `--workspace` | 主扫描根之外的额外工作区 | v4.44.0 | `checks.py` `gen_skill_index.py` `laya_client.py` |
| `--skill-dir` | 被操作对象的根目录（历史命名：单个技能目录） | v4.44.0 | `checks.py` |
| `--skills-dir` | 被操作对象的根目录（历史命名：技能库根） | v4.44.0 | `checks.py` `external_skill_lint.py` |
| `--kb-root` | 被操作对象的根目录（历史命名：知识库根） | v4.44.0 | `memory_handoff.py` `kb_learn.py` |
| `--scripts-dir` | 被操作对象的根目录（历史命名：脚本目录） | v4.44.0 | `iface_lint.py` |

后四行是本次实测扫出来的**未被任何契约覆盖**的根路径参数。它们语义上都属「被操作对象的根」，
按 §2.1 的登记制补登，**不改名**（改名会破坏既有调用面）。**新增脚本请用 `--root` 或 `--base`**，
不要新增 `--xxx-dir` 变体 —— C3a 会把它判成未登记。

### 2.3 每个参数必须有 help 文本

`add_argument` 缺 `help=` 时，`--help` 输出只剩参数名，调用方无法判断语义。C3 对此判 FAIL。
内部参数（`argparse.SUPPRESS`）不在此列。

## 三、输出契约

### 3.1 人读输出

`main` 路径的 stdout 供人阅读。约定：结论行以 `[ OK ]` / `[FAIL]` / `[SKIP]` / `[WARN]` 开头
（`checks.py` 系列的既有格式），其余脚本沿用各自的既有格式，**本次不做格式统一** ——
统一格式属于展示层重构，与本契约要解决的"语义不明"是两件事。

### 3.2 机器可读输出

支持 `--json` 的脚本，`--json` 时 stdout 必须是**合法 JSON 且不含其他文本**（诊断信息走 stderr）。
本版**不设**针对此条的机器判据：校验输出合法性需要逐脚本实跑，归各脚本自己的 `--selftest`；
校验「文档声明 vs 实现」的启发式已在 §6 的 C4 说明里证明会造假信号。

**`--json` 覆盖率是状态量，不是判据**：当前 11/32 个可执行脚本支持。不设覆盖率门槛 ——
有些脚本输出的是给人看的过程摘要，硬加 `--json` 只会产出没人消费的字段。

## 四、兼容性策略

| 情形 | 处置 |
| --- | --- |
| 新增可选参数 | 直接加，向后兼容 |
| 新增子命令 | 直接加，向后兼容 |
| 重命名参数 | **旧名保留为别名**（`add_argument("--new", "--old")`），并在本文 §5 登记弃用；至少保留一个大版本 |
| 删除参数 | 需用户确认（属破坏性变更），并在 §5 登记 |
| 修改退出码语义 | 禁止。四码语义是契约本体，改它等于换一套接口 |
| 修改默认值 | 必须保留回退开关，并把旧口径逐字节复现作为验收证据（反模式清单第 33 条） |

本次（v4.44.0）**没有做任何破坏性变更**：没有重命名、没有删除、没有改默认值。
唯一的接口面新增是 `iface_lint.py` 自身（新脚本，无历史调用方）。

## 六、机器判据映射

| 编号 | 判据 | 级别 | 对应章节 |
| --- | --- | --- | --- |
| C1 | 每个可执行脚本的 `ArgumentParser` 有非空 `description` | FAIL | §2.3 |
| C2 | `main` 路径上的退出码 ⊆ {0,1,2,3} | FAIL | §1 |
| C3a | 根路径参数名已在 §2.2 登记 | FAIL | §2.1 |
| C3b | 每个 `add_argument` 带 `help` | **WARN**（存量 72 处欠账） | §2.3 |
| C4 | `--json` 覆盖率 | **信息项，不作门禁** | §3.2 |
| C5 | 每个可执行脚本在 `references/ops.md` 与 `SKILL.md` 命令块中均有登记 | FAIL | 文档同源 |

**C4 为什么从门禁降为信息项**（本次实测的判据缺陷）：首版想校验「文档声明 `--json` 的脚本是否真有该参数」，
用「同一行内脚本名与 `--json` 共现」做谓词，在真实仓上判出 2 个 FAIL。逐个核对后**两个都是假信号** ——
`ops.md` 第 46 行是 `outbound_scan.py` 的表格行，其中同时提到「已被 `push_router.py` 导入」和
`outbound_scan.py ... --json`，共现谓词于是认定 `push_router.py` 声称支持 `--json`。
从自然语言文档可靠抽取接口声明需要结构化标注，本版不做。**宁可少一条判据，不留一条会造红色假信号的判据。**

**C3b 为什么首版只判 WARN**：实测 72 处 `add_argument` 无 `help`（`check_vector_export.py --json`、
`checks.py --skill-dir` 等）。这是存量欠账，不是本次引入；一次性补齐会牵动 20+ 文件，
且 `help` 文本质量无客观 oracle。登记为欠账，待补完后再议升级，**不预设时间表**。

运行：`python scripts/iface_lint.py --check`（rc=0 全过；rc=1 有 FAIL）。

## 七、诚实边界

1. **只判结构，不判语义合理性**。C1–C5 能抓「描述缺失」「退出码越界」「参数没登记」，
   抓不到「描述的语义是错的」「这个退出码用在这里合不合适」。后者靠人审。
2. **C5 是字面覆盖**。脚本名在 `ops.md` 里出现即算登记，不检查说明文字是否与实现一致。
   真正的同源保证来自 `checks.py skill` 的文档引用完整性判据与本契约的 §2.2 语义表。
3. **C2 的射程依赖 `main` 路径识别**。若某脚本把退出逻辑藏进 `main` 之外的辅助函数并由
   `main` 转调，扫描器可能漏计。这类情形在 `iface_lint --text` 的输出里表现为「退出码为空」，
   人工核对时可按此线索排查。
4. **契约不覆盖第三方上游脚本**（`diagram-design` 的 export_svg.py 等）。它们不属本仓，
   不适用本契约，也不应被 `iface_lint` 计入。
5. **已知偏差（本轮不改，如实登记）**：`publish_tools.py` 把网络/API 失败归为 `FAIL`（rc=1），
   按本契约应为 `3`（无法判定）。不改的理由是它**不崩栈**——诊断信息里带 HTTP 状态码，
   操作者可区分「网络不通」与「内容不符」；而修正需引入第五种结果态（当前只有
   OK/WARN/FAIL/SKIP），会波及汇总口径与 `verify` 子命令，属独立改动。
   症状留痕：真出网络问题时，它会报 `推送失败 …：HTTP 502` 而不是「结论未知」。
   `push_ontology.py` 已在 v4.44.0 修正（`gh()` 抛 `Undecided` → 顶层 `run_cli()` 映射为 3）。
