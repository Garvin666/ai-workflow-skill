## 二、P0 明细：`http_fetch.py --github-search`

**为什么零依赖**：`fetch()` 已自带 token 读取、限流退避、缓存、并发，`/search/repositories` 返回字段与现有 `GITHUB_FIELDS` 同源，解析与输出整段复用。

新增内容：
```python
SEARCH_ENDPOINT = "https://api.github.com/search/repositories"
SEARCH_SORTS = ("stars", "forks", "updated", "help-wanted-issues")
SEARCH_PER_PAGE_MAX = 100    # per_page 官方上限
SEARCH_RESULT_CAP = 1000     # 官方：每次搜索最多 1000 条
SEARCH_QUERY_MAXLEN = 256    # 官方：q 长度上限
SEARCH_BOOL_MAX = 5          # 官方：AND/OR/NOT 数量上限
SEARCH_SCOPE_CAP = 4000      # 官方：最多扫描 4000 个匹配仓库

def github_search(query, sort="stars", limit=30, token=None, use_cache=True, ttl=CACHE_TTL) -> list[dict]
```

内置的保护（都不是装饰，每条都对应一个真实误用风险）：

| 保护 | 防的是什么 |
| --- | --- |
| 未设 `GITHUB_TOKEN` → 显式告警（匿名 10 次/分钟 vs 认证 30 次/分钟） | 连续搜索静默打满限流 |
| q > 256 字符 / 布尔算子 > 5 个 → 告警 | 触发 `Validation failed` 却不知原因 |
| `--search-sort` 非法值 → 回退 best match 并告警 | 静默用错排序 |
| **空结果 → 显式告警「不要因空结果就编造仓库」** | 这是本次调研抓到的真实失效模式（子代理编造链接） |
| `total_count > 1000` → 提示官方上限 | 误以为"只有 1000 个" |

**实测证据**（真实调用，非模拟）：

| 测试 | 命令要点 | 结果 |
| --- | --- | --- |
| 主题搜索 | `--github-search "code search in:name,description language:rust stars:>500" --search-limit 8` | 命中 12 个，取回 8 条，**并搜出子代理漏掉的项目**：`alexpovel/srgn`（911★ MIT「理解语法的 grep」）、`ctxrs/ctx`（1,086★）、`xerj-org/xerj`（1,904★）；`BloopAI/bloop` 被正确标记 `archived=是` |
| 按新鲜度排序 | `topic:code-search pushed:>2026-06-01 --search-sort updated` | 命中 573 个，正确按 `pushed_at` 倒序 |
| 空结果防护 | `--github-search "zzzz-nonexistent-topic-xyz"` | 正确输出「命中 0 个」+ 告警，退出码 0 |
| JSON 输出 | `--json` | 含 `topics` 等完整字段 |

## 三、P1a 明细：`scripts/data_query.py`（新增）

四个子命令，各自解决一个具体问题：

| 子命令 | 作用 | 为什么需要 |
| --- | --- | --- |
| `files` | 目录概览：文件数 / 总大小 / 按扩展名分布 / 最大文件 | **先看数据长什么样再选检索路线**。实测：`E:/ChatGPT/量化分析与数据分析` 有 **121,146 个文件 / 11.16 GB** |
| `big` | 列超过阈值的大文件 | 快速定位该用 `sql` 直查的对象 |
| `find` | 跨文件正则检索（DuckDB `read_text` + `regexp_matches`，带行号） | 替代 Python 逐文件循环 |
| `sql` | 对 Parquet/JSON/CSV **零导入**直接跑 SQL | 核心能力，替代"先导入数据库" |

**实测证据**：

| 测试 | 规模 | 耗时 |
| --- | --- | --- |
| Parquet 全表聚合 | **470 MB / 1,710 万行 / 5,665 只标的** | **1.53 秒** |
| 跨文件正则 `find` | 41 个文件、带行号 | 2.2 秒 |
| 目录概览 `files` | 121,146 个文件 | 23.7 秒（磁盘元数据扫描成本，一次性用于选路） |
| SQL 失败提示 | 列名不存在时 | 1.7 秒内给出可执行 hint |

## 四、本次开发中修掉的 2 个 bug（均由实测暴露）

### bug 1：glob 相对 **CWD** 而非 `--path` 解析 → 静默零命中
`read_text('**/*.md')` 按当前工作目录解析。从技能目录调用去扫 `E:/ChatGPT/工作流/tasks` 时，**不报错、直接 0 命中**，极易误判为"没有该内容"。
修复：`glob_abs = f"{os.path.abspath(root)}/{glob}"`。

### bug 2：用 `json.dumps` 拼 SQL 字面量 → 中文被转义 + 双引号是标识符
```python
# 错误（两个坑叠加，导致零命中）
glob_lit = "[" + ", ".join(json.dumps(g) for g in glob_abs) + "]"
# 产出：["E:/ChatGPT/\u5de5\u4f5c\u6d41/tasks/**/*.md"]   ← 中文被转成 \uXXXX，且双引号在 SQL 中是标识符
```
实测：双引号版 `glob([...])` → **0**；单引号版 → **41**。
修复：新增 `_sql_str()`，用单引号 + `''` 转义。

### 附带加固：glob 零匹配防呆
DuckDB **不支持 `{a,b}` 花括号展开且静默零命中**（实测 `**/*.{md,txt}` → 0，与逐个扩展名相加 32 不符）。现已先 `SELECT count(*) FROM glob(...)` 预检，为 0 直接报错并提示"不支持花括号"。默认扫描改为**显式展开的 57 条 glob 列表**。

## 九、v2.4.1：ast-grep 实装修正（P2 落地后实装验证）

用户确认后安装 `ast-grep-cli` 进 venv，实装过程发现 3 处需修正：

| # | 发现 | 处理 |
| --- | --- | --- |
| 1 | **`sg` 命令已废弃**（运行即打印 `WARNING: sg is deprecated. Use ast-grep instead.`） | 文档全部改用 `ast-grep`；`sg.exe` 虽同在 Scripts 下但不再推荐 |
| 2 | **`ast-grep outline` 提供符号级检索**（列变量/函数/导入/成员） | **原调研中"要引入 ctags 做符号检索"的需求被它覆盖 → 少一个依赖**，不再需要 ctags |
| 3 | `except:` 单独作 pattern 报 `Multiple AST nodes are detected` | 记录为排障项：**复合语句必须写全**（`try: $$$B except: pass`），且该报错**不是语法错**，极易被误判为"不支持 Python" |

**实装后实测（均为真实执行）**：

| 测试 | 命令 | 结果 |
| --- | --- | --- |
| 多节点捕获 + 参数约束 | `ast-grep run -p 'print($$$A, file=sys.stderr)' -l py scripts/` | **10 处命中**（正则难以表达这种带嵌套括号与逗号的参数约束） |
| 跨行复合语句 | `ast-grep run -p 'def $NAME($$$ARGS): $$$BODY' -l py scripts/data_query.py` | 命中并输出**整段函数体**（含内部 try/except/print），证明跨行匹配生效 |
| 符号级检索 | `ast-grep outline scripts/http_fetch.py` | 正确列出常量与函数清单 |
| 失败用例 | `-p 'except: $$$B'` | 报错清晰、给出文档链接，未崩溃 |
