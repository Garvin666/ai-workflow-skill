## 二、现状体检：ai-workflow 现在的检索是「能取不能搜」

体检对象是 v2.3 现有脚本（只读，未改动）：

| 检索对象 | 现有手段 | 真实短板 |
| --- | --- | --- |
| 网页 | `http_fetch URL --grep/--max-chars` + 缓存 | 只能抓**单页**；`--grep` 是**行级正则**，跨行/结构化搜不到 |
| **GitHub** | `--github-repo a/b,c/d` 并发取指标 | ⚠️ **只能"取"不能"搜"**——必须先知道仓库名；无仓库搜索、代码搜索、按 star/语言/时间筛选 |
| 本地文件 | 内置 Glob / Grep（行级正则） | 无索引；1.4GB 的 `code_review_data` 基本搜不动 |
| 文档（PDF/docx/xlsx） | `office_io` 提取文本 | 提取后不落索引，**每次重读**，无法跨文件检索 |
| 历史任务 / 记忆 | `checks.py status` + 翻文件 | 无全文索引，靠人工翻 |
| 代码语义 | 无 | 只能正则，无 AST 结构检索、无向量检索 |

**归纳为 4 个缺口（本报告的调研骨架）**：P0 GitHub 只能取不能搜 → P1 无本地索引层 → P2 仅行级正则 → P3 多来源无去重聚合。

## 三、核心结论

1. **P0 是最高 ROI，而且零依赖**：`http_fetch.py` 的 `fetch()` 已自带 token 读取、限流退避、缓存、并发，而 `/search/repositories` 返回字段与脚本现有 `GITHUB_FIELDS` 同源——**解析与输出可整段复用**。缺的只是一个函数，不是一套架构。
2. **P1 要拆成两半看，结论不同**：
   - **P1a（结构化大数据集）→ 补**，用 DuckDB 直查。对 JSON/CSV/Parquet 零导入跑 SQL，还带 `filename` 伪列可回溯来源。
   - **P1b（自由文本/大仓库索引）→ 实测后降级为"暂缓"**。原以为 `ugrep --index` 是低成本正解，但实测发现**其索引器组件 `ugrep-indexer` 已停更 14 个月、仅 84★**；其余真索引方案要么需常驻服务（重）、要么 Windows 未验证。
   - **关键反例**：**ripgrep 至今没有索引能力**（索引 RFC #1497 未落地）——对 1.4GB 数据集指望 `rg` 是方向性错误。
3. **P2 只值得加一个工具：ast-grep**。它是唯一同时满足「许可宽松 + Windows 原生 + 可离线 + 能表达跨行顺序与否定 + 无需预建数据库」的方案；两个常见替代各有硬伤（comby 实测停更、CodeQL 许可不合规）。
4. **P3 不该新增工具**。为"给报告链接去重"上 Elasticsearch/向量库是把手段当目的；把它固化为 SOP 即可。
5. **三条方法论教训（比选型结论更可复用）**：
   - **子代理的链接不可信**：140 条探活查出 **3 条 404**，其中一条是**编造的日期型假链接**（站点根 200、该路径 404、原文自带省略号），且它正被用来支撑一条结论。
   - **star 数不能代替活跃度**：`ugrep` 本体 3,284★ 且 2026-08-31 有提交，看起来健康；但它的**索引器 `ugrep-indexer` 只有 84★ 且停更 14 个月**。star 高的仓库，其**子组件**可能是死的——必须逐组件核实 `pushed_at`。
   - **许可证字段不足以判断可用性**：`codeql` 仓库标 MIT（只覆盖查询与文档，CLI 引擎另有专有许可）；`meilisearch`/`livegrep`/`opengrok` 显示 `NOASSERTION`（不是"无许可证"，是 GitHub 无法自动判定）。**必须人工核实，不能只看字段。**

## 四、候选方案对比（按缺口组织）

### P0｜GitHub 搜索能力

| 方案 | 类型 | 许可证 | 是否需依赖 | 实测结论 |
| --- | --- | --- | --- | --- |
| **GitHub `/search/repositories`** | 官方 API | 无（服务） | **零依赖** | ✅ **已真实调用成功**，选定 |
| `/search/code` 代码搜索 | 官方 API | 无 | 零依赖 | ⚠️ **强制认证**且限流更紧，暂不实现 |
| `gh search repos`（GitHub CLI） | CLI | MIT | 需 subprocess + 登录态 | ❌ 比直接调 API 更脆 |
| PyGithub | Python 库 | LGPL-2.1 | 加依赖 | ❌ 能力已在 `fetch()` 里，加依赖徒劳 |
| ghapi | Python 库 | Apache-2.0 | 加依赖 | ❌ 同上 |
| github3.py | Python 库 | BSD-3 | 加依赖 | ❌ 同上 |

**实测证据（本方案核心依据）**——主代理匿名真实调用该端点：
```
GET https://api.github.com/search/repositories?q=ast-grep+in:name&sort=stars&per_page=3
→ {"total_count":154,"incomplete_results":false,"items":[{"full_name":"ast-grep/ast-grep", ...}]}
```
**结论：不需要任何第三方库、不需要 token 就能搜。**

官方硬限制（必须写进帮助与排障）：结果上限 **1000 条**（10 页 × 100）；查询 **≤256 字符**；布尔算子 **≤5 个**；搜索范围最多扫 **4000 个匹配仓库**；限流 **认证 30 次/分钟 vs 匿名 10 次/分钟**。

**ast-grep 能力边界（实测/官方文档核对）**：规则支持原子规则（`pattern`/`kind`/`regex`）与关系规则（`inside`/`has`/`follows`/`precedes`，可加 `stopBy`/`field`），官方示例本身就是跨行的（`pattern: Promise.all($A)` + `has: { pattern: await $_, stopBy: end }`）。
⚠️ **重要避坑**：`sg` 的 pattern **不支持正则语法**（`foo|bar`、`.*`、`\w`、`[a-z]` 一律无效），要文本匹配时必须**回头用 grep**。

## 六、反例与不推荐清单

1. **ripgrep 无索引** —— 不要指望 `rg` 解决大仓库/大数据集；它的定位是"扫描更快"。（索引 RFC #1497 未落地）
2. **Everything 只索引文件名**，不含内容 —— 常被误当作"全文检索"。
3. **comby 实测停更**（最后提交 2026-06-08）且 Windows 仅 WSL —— 不要选。
4. **CodeQL 许可不合规** —— 能力虽强但不适用于个人工具链。
5. **语义向量检索在本场景被高估**：它只能补"字面不同"，对「先 A 后 B 且中间无 try」这类**结构约束完全无能力**；且索引维护是长期负担。若确要上，只能当**第一跳粗筛**（配 BM25 混合检索、按符号边界切 chunk），不能替代结构化检索。
6. **不要为"报告链接去重"引入搜索引擎**。
7. **厂商/论文的"准确率提升 N%"一律不作为证据**。
8. **已停更、不要选的方案（实测 `pushed_at` 为证）**：`the_silver_searcher/ag`（2024-06-16，停更 2 年+）、`mchaput/whoosh`（2024-01-03，2.7 年）、`microsoft/CodeBERT`（2023-07-09，3 年）。这三个都仍在大量"推荐清单"里被反复提及。

10. **传染性/强 copyleft 许可需先评估**：`typesense`（GPL-3.0）、`sift`（GPL-3.0）、`universal-ctags`（GPL-2.0）、`PyGithub`（实测 **LGPL-3.0**）。若只作命令行调用通常无碍，但**不能与自有代码静态链接或随产品分发**。
11. **许可证字段陷阱**：`codeql` 仓库元数据标注 MIT，但**只覆盖查询与文档**，CLI 引擎受 GitHub 专有许可约束；`meilisearch`/`livegrep`/`opengrok` 显示 `NOASSERTION`，**是"无法自动判定"而非"无许可证"**。任何选型都必须人工打开 LICENSE 核实一次。
