## P0｜GitHub 搜索能力 —— 补，零新依赖

### 为什么这是最高 ROI

现有 `http_fetch.py` 的 `fetch()` 已经自带 **token 读取、限流退避、本地缓存、并发**，而 `/search/repositories` 返回的字段（`stargazers_count` / `license` / `pushed_at` / `language`）与脚本现有 `GITHUB_FIELDS` **同源**——解析与输出可整段复用。查一个能力用的是一次网络往返 + 一个函数，不是一套新架构。

### 实测证据（本方案的核心依据）

主代理已**真实调用**该端点，匿名即可用：

```
GET https://api.github.com/search/repositories?q=ast-grep+in:name&sort=stars&per_page=3
→ {"total_count":154,"incomplete_results":false,"items":[...]}
```

即：不需要任何第三方库、不需要 token 就能搜。缺的只是"脚本里没这个函数"。

### 落地改动点

1. `http_fetch.py` 新增参数 `--github-search "<query>"`（与 `--github-repo` 互斥）：
   - 拼 `https://api.github.com/search/repositories?q={query}&sort={stars|updated}&order=desc&per_page=100`
   - 复用 `fetch()` → 取 `items[]` → 复用现有 TSV 输出函数
   - 新增输出列：`description` / `language` / `topics` / `open_issues`
2. **必须同步加保护**（否则一个任务几轮搜索就打满）：
   - 认证 **30 次/分钟** vs 匿名 **10 次/分钟** → 未设 `GITHUB_TOKEN` 时打印显式警告
   - 记录官方硬限制到 `--help` 与 `ops.md`：**结果上限 1000 条**（=10 页 × 100）、**查询 ≤256 字符**、**布尔算子 ≤5 个**（超限返回 `Validation failed`）、**搜索范围最多扫 4000 个匹配仓库**
3. `--github-search` 与 `--github-repo` 共用一个限流计数器（否则并发任务会互相打爆）。
4. 可选（列为 P0 附属，非必须）：`/search/code` 代码搜索——**该端点强制要求认证**且限流更紧（10 次/分钟），只在"按代码内容找仓库"时才有价值，建议**暂不实现**。

### 依赖候选的裁决

`PyGithub`（实测 **LGPL-3.0**）/ `ghapi` / `github3.py` 三个库**都不需要**：能力已在 `fetch()` 里。`gh` CLI 的 `gh search repos` 需 subprocess + 登录态，反而更脆。**结论：不引入任何库。**

## P1a｜1.4GB 结构化数据集 —— 补，DuckDB 直查

### 为什么选 DuckDB 而不是"建索引"

- 对 JSON/CSV/Parquet 这类**结构化/半结构化**数据，DuckDB 可以**零导入**直接跑 SQL，还提供 `filename` 伪列可回溯"命中来自哪个文件"——这正好解决"1.4GB 数据集搜不动"。
- MIT、进程内（无守护进程）、Windows + Python 友好度最高。对比之下 JVM/常驻服务类（ES/OpenSearch/OpenGroky/livegrep）在本机落地成本高，不列为个人工作流的首选。

### 落地改动点

1. `setup_env.ps1` 依赖清单加入 `duckdb`。
2. 新增 `scripts/data_query.py`：
   - `data_query.py sql "SELECT ... FROM read_json_auto('...')"` —— 直查
   - `data_query.py find --pattern "关键词" --path <dir> --glob "*.json"` —— 全目录文本/正则检索，输出命中文件 + 行 + 上下文
   - 复用 `--max-rows` / `--max-chars` 做输出截断（Token 纪律）
3. **待验证项**（不写死）：DuckDB 的 FTS 扩展在 Windows 上的可用性与中文分词表现，需真机实测后再决定"自由文本"是否也走 DuckDB。

### 反面提醒

DuckDB 是**新依赖**，这违反"零依赖"偏好，所以只用于**大数据集**场景；小文件继续用内置 Grep，不要为了统一而统一。

## P1b｜自由文本 / 大仓库索引 —— 实测后降级为「暂缓」

### 原推荐与它为什么被推翻

初稿基于"`ugrep --index` 是唯一内建真索引 + 支持增量的 CLI grep"，判定为最小代价路径。**但批次 2 实测推翻了它**：

| 组件 | star | 最后提交 | 判读 |
| --- | --- | --- | --- |
| `Genivia/ugrep`（本体） | 3,284 | 2026-08-31 | 看似健康 |
| **`Genivia/ugrep-indexer`（索引器）** | **84** | **2025-06-22** | ⚠️ **停更 14 个月 + 用户群极小** |

**索引能力依赖的是后者**。一个 84★、14 个月无提交的组件，不适合作为工作流的基础依赖。
→ **教训：star 数不能代替活跃度，必须逐组件核实 `pushed_at`。**

### 其他候选为什么也不立刻上

| 候选 | 实测结论 | 阻塞点 |
| --- | --- | --- |
| `google/codesearch` | 4,008★ BSD-3-Clause，2026-08-30 活跃 | **Windows 支持未验证** |
| `tantivy` / `tantivy-py` | 16,056★ MIT，活跃 | 自建索引工程量大（分词/增量/索引生命周期全要自己管） |
| `sourcegraph/zoekt` | 1,880★ Apache-2.0，活跃 | Windows 未验证 |
| `hound` / `livegrep` / `opengrok` / ES / Meilisearch / Typesense | 多为常驻服务 | 个人工作流上守护进程不划算；且 `livegrep`/`opengrok` 许可为 `NOASSERTION` 待核 |
| `sqlite FTS5` | 内置、无依赖 | 需自建索引层，同样有工程量 |
| `mchaput/whoosh` | ⚠️ **停更 2.7 年**（2024-01-03） | 排除 |

### 修正后的结论

**暂缓 P1b，先做 P1a（DuckDB）**。理由：1.4GB 数据集主要是结构化/半结构化，DuckDB 已覆盖最高频场景；而自由文本大仓库的索引，目前没有"轻量 + 活跃 + Windows 可用"三者兼备的方案。

**重新启动 P1b 的触发条件**（满足任一）：
1. 实测确认 DuckDB 的 FTS 扩展在 Windows 上可跑且中文分词可接受 → 直接用 DuckDB，问题终结；
2. 出现"必须对非结构化代码仓库做秒级全文检索"的真实任务 → 那时再实测 `google/codesearch` 或 `tantivy`；
3. `ugrep-indexer` 恢复活跃提交 → 可重新评估。

### 关键反例（务必记录）

**ripgrep 至今没有索引能力**（索引 RFC #1497 未落地，master 仅"indexing scaffolding"脚手架）。对 1.4GB / 大仓库指望 `rg` 靠"扫得更快"解决，方向就是错的。同时 `ag`（停更 2 年+）、`whoosh`（2.7 年）也已在候选外。

## P2｜结构化 / AST 检索 —— 补，且只加一个：ast-grep

### 为什么是它（唯一同时满足 4 个硬条件）

| 条件 | ast-grep | comby | CodeQL | semgrep |
| --- | --- | --- | --- | --- |
| 许可证宽松 | ✅ MIT | ✅ Apache-2.0 | ❌ CLI 引擎受专有许可（仓库元数据虽标 MIT，仅覆盖查询与文档） | ⚠️ LGPL-2.1 |
| Windows 原生 | ✅ | ❌ 仅 WSL | ⚠️ | ✅ |
| 可离线 | ✅ | ✅ | ⚠️ 需建库 | ✅ |
| 能表达跨行顺序与否定 | ✅ `follows`/`precedes`/`not` | ✅ | ✅ | 部分 |
| 无需预建数据库 | ✅ | ✅ | ❌ | ✅ |
| 维护状态 | ✅ 实测 2026-09-09 仍有提交 | ⚠️ **实测最后提交 2026-06-08** | ✅ | ✅ |

**comby 停更风险已被实测坐实**（最后提交 2026-06-08，距今约 3 个月），**CodeQL 许可不合规**，故不选。

### 落地改动点

1. 在 `SKILL.md` 阶段 3「精确检索」条增加**决策规则**：
   > 文本/正则 → 内置 `Grep`；**跨行/结构模式（"先 A 后 B 且中间无 try"这类）→ `sg`（ast-grep）**；符号级"谁引用了这个方法" → `sg` 或 ctags。
2. `references/ops.md` 脚本速查表加 `sg` 条目与 3 个典型查询示例。
3. **必须写进避坑**：`sg` 的 pattern **不支持正则语法**（`foo|bar`、`.*`、`\w`、`[a-z]` 一律无效），要文本匹配时**回头用 grep**。这条不写清必然踩。
4. **不新增 Python 封装层**：`sg` 以 CLI + `pip install ast-grep-cli` 调用即可，包一层只会增加维护面。

## P3｜多来源去重聚合 —— 不新增工具，固化为 SOP

### 结论

不要为了"给报告链接去重"上 Elasticsearch 或向量库——这是把手段当目的。本次实战已经跑通了最小可行流程，把它固化即可：

```
提取 → 去重 → 探活 → 分类标注
grep -ohE "https?://..." findings-*.md | sort -u > all_urls.txt
http_fetch.py --check-links all_urls.txt --concurrency 8
```

### 落地改动点

1. `references/ops.md` 新增一节「链接收集与核验 SOP」，把这四步写死。
2. **新增一条硬规则**（本次有血的教训）：**子代理产出的链接必须全量探活后才可进交付物**。本次 140 条探活查出 **3 条 404**，其中一条 `magicliang.github.io/2026/04/17/...` 是**子代理编造的日期型假链接**（站点根 200、该路径 404，原文还带省略号）。
3. 探活结果必须**区分三类**，不可混为一谈：
   - `404` = 真失效（必须修）
   - `403/429` = 反爬或限流（**不是失效**，标注即可）
   - `ERR 502 Tunnel` = **本机出口隧道问题**（见下）

## 附：本次发现的环境事实（应写入 ops.md 排障表）

以下域名在本机**稳定返回 502 `Tunnel connection failed`**，属**本地出口/代理限制，非站点失效**：
`huggingface.co`、`jina.ai`、`console.cloud.google.com`

→ 影响：以后任何涉及 HuggingFace / Jina / GCP 控制台的调研，都不应把 502 判为"站点挂了"，应标注「本机环境无法验证」。**这是本次新增的可复用事实。**
