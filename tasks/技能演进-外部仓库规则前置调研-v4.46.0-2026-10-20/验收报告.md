## 3. 借鉴落点（调研 → 实现的一一对应）

| 调研得出的东西 | 落到哪 | 怎么用的 |
| --- | --- | --- |
| `community/profile` 一次返回 6 类文件、匿名可读、认得 `docs/contributing.md` | `probe_community()` | 主路径直接取；`files.*.url` 原样透出，不自己拼路径 |
| `rulesets` 列表不含规则内容 | `probe_rulesets()` | list → 只对 `enforcement=active` 取详情（`--detail-limit` 默认 3，防 N+1） |
| `branch protection` 的 404 有两义 | `_classify_status()` | 按 message 分态：`not protected` → 无；`Not Found` → 未检测 |
| AGENTS.md 的「就近覆盖」语义 | `probe_agent_files()` 的候选顺序 | 根层 4 个候选按优先级，再探 `.github`、`.cursor`；命中标 priority |
| Aider「单文件显式载入」优于全树扫描 | 全脚本约束 | 只报 `size`/`url`，**不拉正文**，避免 token 黑洞 |
| CLA/DCO 无仓库级 API | 契约 §6.3 | 明确不输出这两项「有/无」，只留间接推断口径 |
| commitlint「规范要能落到可执行命令」 | 契约 §5 | 治理信号要求配「本地怎么先跑一遍」，不写空话 |
| `health_percentage` 是元数据完整度 | 契约 §6.5 ＋ SKILL.md 流程条目 | 两处都写明**禁止当质量指标** |
| `code_search` 配额只有 core 的 1/500 | 设计取舍 | 全部走 contents/community 等 core 端点，不用 search 探文件 |

## 5. 已知局限（不掩盖）

1. `community/profile` 只认 GitHub 认可路径，对方写 wiki 时返回「无」——**假阴性**，未解。
2. `agent_files` 只探三层，monorepo 子目录的 AGENTS.md 会漏。
3. `branch protection` 在有 rulesets 的仓上必然 404，脚本报「未检测」并提示以 rulesets 为准。
4. CLA/DCO 不输出「有/无」（无仓库级 API）。
5. `rulesets` 的 `bypass_actors` 未解析。
6. 无磁盘缓存：同仓重复调用会重发请求（每仓约 5–7 次 core）。
7. `rulesets` 匿名可读性未实测（本次仅带 token 验证）。

## 6. 复盘

- **返工最多**：文档引用完整性（1 次）。根因是「反引号内的文件名按技能根扁平解析」这条既有口径，写文档时按常识写文件名就会撞。
- **被推翻的假设**：「`branch protection` 的 404 就是没有保护」——实测发现两种 message，这条直接改变了脚本判据，也是本次最有价值的产出。
- **踩的坑**：`gh api search/code` 返回 HTML（代理劫持），于是放弃用 code search 找实现，改用端点实测 + 规范页原文。意外印证了调研结论「不要依赖 code_search」。
- **下次可省的一步**：`gh api` 能用时不必再写 curl 匿名对照；这次为验证「匿名可读」多花了一次请求，但结论有用（写进了契约），不算冗余。
