# 调研报告：外部仓库规则前置调研（v4.46.0 前置拆解）

> 任务：为 ai-workflow 补一条「涉及外部仓库时先摸清对方规则」的能力。
> 取数时间：2026-10-20 22:20–22:35（GMT+8）｜执行机：本机 Windows｜凭据：gh CLI 已登录 `Garvin666`
> 证据分级：【本机实测】= 本次真实请求的原始返回；【官方推荐】= GitHub/上游文档明示；【实践观点】= 项目自述或社区用法，未经我复现。

## 0. 结论先行

1. **不需要自己发明规则清单**：GitHub 有一个被严重低估的端点 `GET /repos/{owner}/{repo}/community/profile`，一次调用返回 6 类协作文件的**存在性与 URL**（contributing / code_of_conduct / issue_template / pull_request_template / license / readme），且**匿名可读**（实测 HTTP 200）。这比原方案「逐路径探三个文件」少 5 次请求，而且认得 `docs/contributing.md` 这种非根目录位置。
2. **治理规则要分两档读**：`rulesets` 对 public 仓可读，但**列表不含规则内容**，必须二次请求 `/rulesets/{id}` 才拿到「要求 1 个 approval + code owner review + cla 检查」这种可执行约束。
3. **最危险的坑是 `branch protection` 的 404**：同一个 404 有两种含义——`Not Found`（看不到/不存在）与 `Branch not protected`（确实没保护）。**只看状态码必然把「没权限」误判成「没规则」**，这是本次调研对判据设计影响最大的一条。
4. **AGENTS.md 生态值得借的是「就近覆盖」语义**，不是文件格式：monorepo 在子目录放第二个 AGENTS.md，agent 读**目录树上最近的那个**，近的覆盖远的。这条可直接落到脚本的「多层级探测」里。
5. **DCO/CLA 没有仓库级 API**：它发生在 PR 事件与 CI 里，仓库元数据查不到。脚本对这类只能报「未检测」，不能报「无」。

## 1. 需求边界（要解决什么、不解决什么）

| 要解决 | 不解决 |
| --- | --- |
| 动手前知道对方有没有 CONTRIBUTING / PR 模板 / CoC / 许可证 | 不替用户判断「这条规则合不合理」 |
| 知道默认分支是否被 ruleset 保护、要求哪些检查 | 不试图绕过保护，也不代改规则 |
| 知道对方用什么 agent 指令文件（AGENTS.md / CLAUDE.md / CONVENTIONS.md） | 不解析指令全文并据此自动改代码 |
| 知道当前 token 的配额余量，避免撞限流后误判成故障 | 不做自动重试以外的配额管理 |

## 2. 平台能力实测

### 2.1 `community/profile`：一次拿全协作文件

实测 `GET /repos/openai/codex/community/profile`【本机实测】：

```json
{"health_percentage":62,
 "files":{
   "code_of_conduct":null,
   "contributing":{"url":".../contents/docs/contributing.md",
                   "html_url":".../blob/main/docs/contributing.md"},
   "issue_template":null,
   "pull_request_template":null,
   "license":{"spdx_id":"Apache-2.0"},
   "readme":{"url":".../contents/README.md"}}}
```

三个可用信号：

- **`files.*` 为 null 即「没有」**，非 null 直接给 URL —— 不需要自己拼路径、也不需要 `--check-links` 探活。
- 它认得**非根目录**的贡献文件：codex 的 CONTRIBUTING 在 `docs/contributing.md`。自己拼 `/CONTRIBUTING.md` 会漏。
- `health_percentage` 是**元数据完整度**，不是治理严格度（codex 62 分却有 2 条强制 ruleset）。**不能当质量指标用**。

匿名可读性实测【本机实测】：不带 token 请求 `aider-ai/aider/community/profile` 返回 **HTTP 200**，字段齐全。意味着这一步在 CI 或未登录环境也能跑。

### 2.2 `rulesets`：列表给名义，详情给约束

`GET /repos/openai/codex/rulesets`【本机实测】返回数组，每项含 `id / name / target / enforcement`：

```json
[{"id":6735016,"name":"CI must pass to merge to main","target":"branch","enforcement":"active"},
 {"id":21660955,"name":"Restrict pushes","target":"branch","enforcement":"active"}]
```

`GET /repos/openai/codex/rulesets/6735016`【本机实测】才给出真正能用的约束：

```json
{"rules":[
  {"type":"deletion"},
  {"type":"non_fast_forward"},
  {"type":"required_status_checks","parameters":{
     "required_status_checks":[{"context":"cla"},{"context":"CI required"}]}},
  {"type":"pull_request","parameters":{
     "required_approving_review_count":1,
     "require_code_owner_review":true}}]}
```

**这条直接决定脚本形状**：只打列表 = 只知道「有条规定叫 CI must pass」；打了详情才知道「必须过 cla 与 CI required、1 个 approval、要 code owner 审」。所以实现里必须做「列表 → 对 active 项取详情」，且要限制请求数（details 只对 `enforcement=active` 取，避免 N+1 打爆配额）。

### 2.3 `branch protection`：404 有两义（本次最重要发现）

同一端点三种返回【本机实测】：

| 场景 | 状态码 | message |
| --- | --- | --- |
| `anthropics/claude-code`（无 admin） | 404 | `Not Found` |
| `Garvin666/ai-workflow-skill`（有 admin，未设保护） | 404 | `Branch not protected` |
| `repos/.../actions/permissions`（权限不足端点） | **403** | `You must have repository read permissions…` |

**结论：状态码不足以区分「看不到」与「没有」。** 判据必须读 `message` 文本，且把它落成三分态：

- 200 → `有保护`（附必填检查与审批数）
- 404 + `Branch not protected` → `无保护`（这是真的没有）
- 404 + `Not Found` ／ 403 → `未检测（权限不足或仓库/分支不存在）`

如果不做这个区分，脚本会把自家仓「没设保护」和别人的仓「不给你看」报成同一件事——而这正是「未检索不得说不存在」在实现层的落点。

### 2.4 配额

`GET /rate_limit`【本机实测】：core `5000/剩余 4999`、search `30/30`、code_search `10/10`。**code_search 配额比 core 小两个数量级**，任何「靠 code search 找文件」的探测思路都会先撞墙。所以脚本一律走 contents/community 这类 core 端点，不走 search。

### A. `agentsmd/agents.md` —— 借「就近覆盖」，不借文件格式

原文【官方推荐】：*"Agents automatically read the nearest file in the directory tree, so the closest one takes precedence"*，monorepo 每个 package 可放自己的 AGENTS.md。

- **可复用思路**：规则的作用域是**目录树上的最近祖先**，不是全仓唯一。
- **可复用片段**：它给旧工具留了兼容做法 `mv AGENT.md AGENTS.md && ln -s AGENTS.md AGENT.md` —— 说明「同一物理量两个文件名」是真实存在的历史债，探测时要**两个名字都查**。
- **局限**：这是「agent 怎么读指令」的规范，**不管协作流程**（PR 模板、CLA、分支保护都不在射程）。只能覆盖「指令面」，不能覆盖「治理面」。

### B. `openai/codex` —— 证明这个格式已经是事实标准

- 130k star、当日仍有推送，AGENTS.md 在根目录与子项目均有分布（规范页称主 OpenAI 仓有 88 个）。
- **可复用判断**：探测 agent 指令文件时，`AGENTS.md` 应排在 `CLAUDE.md`、`CONVENTIONS.md` 之前——不是因为更好，而是因为**跨工具覆盖面最大**（规范页列出 20+ 工具支持）。
- **局限**：它对「读到了之后怎么合并」有自己实现，但没公开成通用库；我们只借优先级顺序，不借其代码。

### C. `Aider-AI/aider` —— 单文件 + 显式 read

Aider 的做法是把 `CONVENTIONS.md` 通过配置 `read: AGENTS.md` 载入。【实践观点】

- **可复用思路**：**单文件、显式声明**比「自动扫描全目录」更可预测，也更省 token。
- **对本需求的意义**：探测脚本只报「有哪些文件」，**不自动把全文读进上下文**——读多少由使用方决定。这条约束要写进契约，否则脚本会变成 token 黑洞。

### D. `cla-assistant/cla-assistant` —— CLA 是事件，不是元数据

- 它的校验发生在 PR 打开/更新时（webhook → 状态检查），**仓库元数据里查不到 CLA 是否要求**。
- **可复用思路**：把「仓库级可查」与「事件级不可查」分开。CLA/DCO 归后者，脚本只能给出**间接信号**（`.github/CLA.md`、`.github/workflows/` 里是否出现 dco/cla 关键字），且必须标「推断，未验证」。
- **局限**：任何声称「CLA 已确认」的自动结论都是过度断言。

### E. `conventional-changelog/commitlint` —— 规范要能落到一条可执行命令

- 它的价值不在规则本身，而在**把「commit 要符合 X」变成一条可跑、可失败的检查**。
- **可复用思路**：调研产出不该只写「对方要求 conventional commits」，而应写「对方有 `commitlint.config.js`，本地可跑 `npx commitlint --from …`」——**规则后面必须跟一个可执行的验证命令**，否则等于没调研。
- **局限**：只有配置存在时才成立；配置在 `package.json` 里也能藏，探测要多看一处。

## 4. 复用决策

| 来源 | 决策 | 理由 |
| --- | --- | --- |
| GitHub `community/profile` | **直接复用** | 官方端点，语义稳定，匿名可用，一次拿全 |
| GitHub `rulesets` list + detail | **直接复用（两段式）** | 列表轻、详情准；只对 active 取详情控制请求数 |
| `branch protection` | **改造后复用** | 必须按 `message` 分三态，不能按状态码 |
| AGENTS.md 就近覆盖 | **部分采纳** | 采纳「多层探测 + 最近优先」；不采纳「自动读全文」 |
| Aider 单文件显式 | **采纳为约束** | 只报存在性，不拉正文，避免 token 黑洞 |
| CLA/DCO | **不采纳自动判定** | 无仓库级 API，只能给间接信号并标未验证 |
| commitlint | **采纳为产物要求** | 每条规则尽量附可执行验证命令 |
| 自研 | **需要** | 上述能力没有一个现成 CLI 能一次输出「三态 + 摘要 + 配额」，且要符合本技能的接口契约 |

## 5. 借鉴内容在最终实现中的具体用途

| 借鉴项 | 落在哪个文件/位置 | 具体怎么用 |
| --- | --- | --- |
| community/profile 一次取全 | `scripts/repo_rules_probe.py` 的 `probe_community()` | 主路径：拿 6 类文件的存在性与 URL，直接映射成 `有/无` 两态 |
| 非根目录贡献文件 | 同上，`url` 字段原样透出 | 摘要里给 `html_url`，使用者点开即达，不自己拼路径 |
| rulesets 两段式 | `probe_rulesets()` | 先 list，再对 `enforcement=active` 的前 N 条取 detail，抽出 `required_status_checks` 与 `required_approving_review_count` |
| branch protection 404 两义 | `probe_protection()` 的 `_classify_404()` | 读 `message`：含 `not protected` → `无`；否则 → `未检测` |
| AGENTS.md 就近覆盖 | `probe_agent_files()` 的候选顺序 | 按 `AGENTS.md → AGENT.md → CLAUDE.md → CONVENTIONS.md → .cursor/rules → .github/copilot-instructions.md` 顺序探测，命中即停并标注优先级 |
| 不拉正文 | 全脚本约束 | 只取 `size` 与 `html_url`，正文一律不下载 |
| CLA/DCO 只能推断 | 输出字段 `inferred` | 标 `未验证`，不参与「有/无」判定 |
| commitlint 可执行化 | 摘要模板 | 有 `commitlint` 配置时输出一行可跑命令 |
| 配额 | `probe_rate_limit()` | 每次运行打印 core 剩余与 reset，撞限流时不再归因成网络故障 |

## 6. 局限与未覆盖

1. **branch protection 在「用 rulesets 的仓」上必然 404**：这是设计使然（新机制取代旧机制），不代表无保护。脚本对这种情况报 `未检测`，并在摘要里提示「请以 rulesets 为准」。
2. **`community/profile` 只认 GitHub 认可的路径**：如果对方把贡献说明写在 `wiki` 或 `docs/` 外的自定义位置，端点查不到。脚本会标 `无`，这是**假阴性**，已知且未解决。
3. **`rulesets` 的 `bypass_actors` 未解析**：谁能绕过规则不在本次射程。
4. **未验证「匿名 + rulesets」**：本次匿名只测了 community/profile；rulesets 匿名可读性未实测，脚本默认要求 token，无 token 时该项报 `未检测`。
5. **没有做跨仓批量压测**：只测了 4 个仓（codex / claude-code / aider / 自家两仓），样本小，结论限于这些形态。
