## 二、性能明细：`data_query.py` 遍历改 `os.scandir`

### 改了什么

```python
# 旧（v2.4）：os.walk 只给名字 → 每个文件都要再 stat 一次
for dirpath, dirnames, filenames in os.walk(root):
    dirnames[:] = [d for d in dirnames if d not in skip_dirs]
    for fn in filenames:
        out.append(os.path.getsize(os.path.join(dirpath, fn)))   # ← N 次额外系统调用

# 新（v2.4.2）：DirEntry 在列目录时已带回属性，stat() 直接复用
def _walk_stat(root: Path, skip_dirs: frozenset[str]):
    stack = [str(root)]
    while stack:
        cur = stack.pop()
        try:
            with os.scandir(cur) as it:
                for entry in it:
                    try:
                        if entry.is_dir(follow_symlinks=False):
                            if entry.name not in skip_dirs:
                                stack.append(entry.path)
                        elif entry.is_file(follow_symlinks=False):
                            yield entry.path, entry.stat(follow_symlinks=False).st_size
                    except OSError:
                        continue
        except OSError:
            continue
```

### 为什么快（Windows 特有）

`os.scandir` 底层用 `FindFirstFile`/`FindNextFile`，**返回的 `Win32_FIND_DATA` 里本来就带文件大小**。
`DirEntry.stat()` 直接复用这份已到手的数据；而 `os.path.getsize` 会**对每个文件单独发一次 stat 系统调用**。
12 万文件 = 12 万次多余的系统调用 —— 这就是 21s 的来源，与磁盘 IO 无关（预热后依旧 22s）。

### 实测（公平基准，预热后各跑 3 次取最小值）

| 轮次 | 旧 `os.walk`+`getsize` | 新 `os.scandir`+`stat` | 加速比 |
| --- | --- | --- | --- |
| 复现 1 | 22,365 ms（25428/22365/26133） | 2,341 ms（2477/2341/2355） | **9.55×** |
| 复现 2 | 22,875 ms（26070/22875/26278） | 2,278 ms（2380/2298/2278） | **10.04×** |

**取保守值 ≈9.6×**。旧实现即使预热后也从未低于 22s，排除冷缓存假象。原始输出见 `基准-公平对比.txt`，可复现脚本 `_bench_walk.py`。

### 输出一致性（关键）

| 校验项 | 旧 | 新 | 结论 |
| --- | --- | --- | --- |
| 文件总数 | 121,146 | 121,146 | ✅ 一致 |
| 总字节 | 11,982,072,013 | 11,982,072,013 | ✅ 一致 |
| `--top 12` 全量输出逐字节比对 | — | — | ✅ 31 行无差异 |
| `big` 前 12 大文件列表 | — | — | ✅ 一致 |

**结论：纯性能优化，零口径变化。**（这也解释了为什么必须做逐字节比对——只测耗时无法证明没改坏统计。）

### 排障记录（写进 ops.md 的价值）

端到端 `data_query.py files` 热机耗时 **4.0s**，明显高于纯遍历的 **2.3s**，差值来自扩展名聚合 + 排序（约 1.4s）与解释器启动。
→ 教训：**排查性能问题时必须区分「遍历」与「聚合」两段开销**，否则会误以为优化没生效而去改错地方。

## 三、能力明细：`--github-code-search`（官方 `/search/code`）

### 与 `--github-search` 的区别

| | `--github-search` | `--github-code-search` |
| --- | --- | --- |
| 官方端点 | `/search/repositories` | `/search/code` |
| 搜什么 | 仓库名 / 描述 / README / topics | **仓库里的代码内容** |
| 典型问题 | 「有没有做 X 的开源项目」 | 「这个函数在哪些仓库里被这样实现」 |
| 返回 | 仓库 + star/fork/license/语言 | **仓库 + 文件路径 + 命中片段** |
| 认证 | 匿名可用（10 次/分钟） | ⭐**强制认证**，匿名 401 |
| 必需头 | 无 | `Accept: application/vnd.github.text-match+json`（否则无片段） |

### 实测确认的三件事

1. **强制认证是实测出来的，不是照抄文档**：无 token 请求直接返 **401**，**不是限流**。据此脚本**提前拦截**，在发请求前就给出可执行提示（设 `GITHUB_TOKEN` / 或改用 `--github-search`），不再抛裸 401 堆栈。
2. **片段依赖 Accept 头** → `fetch()` 新增 `headers_extra` 参数，脚本内置该头。
3. **`--dry-run` 可在无 token 下验证参数构造**，实测输出：

```
$ http_fetch.py --github-code-search "add_dependency repo:fastapi/fastapi" --dry-run
[DRY-RUN] 将请求：https://api.github.com/search/code?q=add_dependency+repo%3Afastapi%2Ffastapi&per_page=30
[DRY-RUN] 附加头：Accept: application/vnd.github.text-match+json
[DRY-RUN] 认证：缺失（该端点需要 token，否则 401）
```

### ⚠️ 诚实标注（未实测部分）

本机**没有配置 PAT**（`GITHUB_TOKEN` 未设置），因此：
- ✅ 已实测：401 分支、URL/参数构造、`--dry-run` 输出、argparse 接线、语法编译；
- ❌ **未端到端实测**：带 token 时的真实响应解析（`items[].repository.full_name` / `path` / `text_matches[0].fragment` 的字段结构）。

字段结构**依官方文档实现**，标注为「未经带 token 的端到端实测」。首次带 token 使用时请核对一次输出列是否有空值。

## 四、可用性明细：`--dry-run`

两个搜索端点通用，只打印将请求的 URL + 附加头 + 认证状态后即返回，**不发请求、不消耗配额**。
用于：① 离线校验限定符拼得对不对；② 确认本地是否已配 token；③ 避免因试参数打满 10 次/分钟的搜索配额。
对非搜索命令（如 `--github-repo`、纯 URL 抓取）使用时会**显式告警本次忽略**，不会静默失效。
